# 回归基线失败挂起门

全量回归的有界执行与存量/引入失败归类：防存量死循环烧穿 run 预算，也让存量失败可快速收口为可判定终态。

## 现行规则

- 全量套件必须经有界入口执行：单次执行带硬超时；超时或检测到测试挂起时中止执行并报出挂起测试的标识（文件/用例名），不得无限期等待自然结束。implementer/repair 契约引导使用该入口执行全量回归，不得仅依赖无超时的裸 `pytest` 调用。
- 存量/本次引入的归类以变更前基线（本 change 首个提交的父提交）的等价执行为依据，不得仅凭文件名/模块名经验推断：失败或挂起在基线复现 → 归类存量（结论中指明基线复现依据）；基线通过而本 change 失败或挂起 → 归类本次引入，不得归为存量。混合情形（既有存量又有引入）判为存在本次引入的回归，不得以存量为由整体放行。
- 失败被归类为存量（与本 change 无关且无法在本 change 范围内消除）后，implementer run 据此收口为可判定终态，不得在同一 run 内反复完整重跑全量套件（除非为收集一次基线对照证据）；收口证据（阻塞测试标识 + 基线复现结论）落于 run 文件与提交信息，可被独立复核。
- 仅存在于主树的自举部署物（`.fenix/hooks/*`、`dist/` 等）在 worktree 中不存在时，依赖这些文件的测试以 skip 处置（skip 原因指明自举物未部署），不得硬失败、不得因此被判为本次引入的回归；主树（自举物已部署）中同一批测试正常执行断言。
