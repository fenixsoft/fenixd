# add-spec-review-gate — 设计方案

## Context

### 当前状态

SPEC 从 `drafted` 到 `ready` 的晋升链由 `add-draft-promotion-gate`（2026-09-08）建立并已落地：

- 配置键 `gates.promote_mode`（`auto`/`manual`）控制是否自动晋升。
- 共享晋升函数 `core/pm_engine/promotion.py:promote_drafted(project_root, spec_name, *, state_machine, logger)` 承载全部晋升前处理：软化不可满足声明（含 dispute 审计留痕）→ 交付物声明 lint → tasks.md 可解析性 lint → 违规则停留 `drafted` 并写 STATE error。
- 四条自动触发路径（`spec_drafted` 事件 / `start_after` 到期 / full_scan recovery / scheduling_kick）收口在 `core/pm_engine/engine.py:_on_spec_drafted` 单点闸口。
- 三条人工通道（Dashboard `POST /api/spec-promote`、`bin/fenix_cli.py promote`、`/fenix-ready` skill）共用同一 `promote_drafted`，收尾各自执行 `transition(spec, "ready")`。

### 缺的是什么

上述全部是**机械校验**：软化管「声明路径是否可满足」，两道 lint 管「声明形态是否合法」「tasks.md 能否解析出行」。没有任何环节判断**方案本身是否成立**——能否达成 proposal 声明的目的、任务拆分是否留了实现漏洞、改动是否会波及其他场景。方案层面的方向性错误只能等实现完成、验证流水线跑完才暴露，代价是一整轮实现 + 验证预算，而框架届时只能给出一堆场景失败证据，无法告诉人「根因是方案当初就想错了」。

该缺口在自进化链路（`self_evolution`）上被放大：框架自动从自省报告提炼需求、批量产出 `evo-*` SPEC 并直接进入自动实现，**这些 SPEC 没有任何人为方案背书**。

### 约束

- 被管项目形态多样，判据 MUST NOT 依赖本框架自托管的目录结构（如 `core/`）。框架既有原则：不做项目级特殊处理。
- 状态是唯一真源（`.fenix/STATE.md`），一切调度决策从文件重建——新机制必须落在这套模型内。
- daemon 崩溃/重启必须能从文件恢复现场，任何新增中间态都要有明确的恢复语义。
- 主树常存多批未提交的人工在途修改（既有事实），任何自动化 MUST NOT 擅自还原主树文件。

## Goals / Non-Goals

**Goals:**

1. 在 `drafted` 与 `ready` 之间插入**方案级评审**，把方向性风险挡在实现之前，把关成本从「一轮实现 + 一轮验证」降到「一次单轮只读评审」。
2. 为自进化产出的 `evo-*` SPEC 提供强制质量保障。
3. 评审结论机械可消费、状态可观测、故障可恢复、误判有逃生门。
4. 评审者能就地修补「可修补的漏洞」，不必为小瑕疵走一遍人工。

**Non-Goals:**

1. **不替代验证流水线**：评审判「方案是否成立」，不判「实现是否正确」。验证闭环职责不变。
2. **不做评审结果的分级采纳**：`rejected` 一律进 blocked 交人工，不引入「部分采纳」的中间态。
3. **不引入评审预算键与阈值旋钮**：重试上限与跳过判据硬编码，`gates.spec_review_mode: never` 作为整体逃生门。
4. **不自动回滚越界写入**：见 D5 的取舍说明。
5. **不改造既有熔断/冻结/合并失败路径**：新 blocked 只增前缀标识，不动既有语义。

## Decisions

### D1 新增 `reviewing` 状态，而非复用 `drafted` 或内联同步调用

**决定**：状态机新增第 11 个状态 `reviewing`，转移边为 `drafted → [ready, reviewing]`、`reviewing → [ready, blocked]`、`blocked → [ready, reviewing]`。

**为何不选「复用 `drafted` + 评审标记字段」**：不新增状态枚举、改动小，但会在 `drafted` 内造出一层隐式子状态（未评审 / 评审中 / 已通过），靠 STATE 字段区分。本框架历史上这类「状态字面量不变、靠字段承载真实语义」的设计正是可观测性事故的高发区——Dashboard 显示 `drafted` 而实际语义已变，recovery 与并发判定都要额外读字段。显式状态换来的是所有既有机制（事件映射、recovery、Dashboard、hook、时间轴）零成本适配。

**为何不选「晋升链内联同步调用」**：改动最小、三条通道自动共用，但晋升发生在 PM Engine 的调度循环内，同步调起一个可能跑数分钟的 `claude` 子进程会阻塞整个事件循环；且 Dashboard/CLI 进程也要同步等待，HTTP 请求可能挂住数分钟。异步 run 是本框架唯一正确的 Agent 执行形态。

**代价**：`VALID_TRANSITIONS` 扩展、事件映射与处理器表新增条目、recovery 分支、Dashboard 状态色板、文档——触及面广。这是本设计最主要的一次性成本。

### D2 分流方向改为「默认全量 + 白名单跳过」

**决定**：默认全部 SPEC 进入评审；仅当四项**全部命中**时跳过——`mode == fast-track` 且 能力目录数 ≤ 1 且 Deliverables 声明条目 ≤ 3 且 非 `evo-` 前缀。

**理由（实测数据）**：原设想是「命中风险特征才评审」。对 `spec/changes/` 的 51 条 SPEC（`spec/archive/` 的 154 条因 `mode` 与声明段是后成规范而不可比）实测各特征命中率：

| 特征 | 命中率 |
|---|---|
| `mode == full` | 62.7% |
| 能力目录数 ≥ 2 | 35.3% |
| 顶层目录数 ≥ 3 | 27.5% |
| 交付物声明条目 ≥ 5 | 54.9% |
| tasks 条目 ≥ 8 | 78.4% |

**`mode == full` 一条即命中 62.7%**，其余特征只是在该基数上继续加码，任何「命中即评」的并集都落在 62%–80% 区间——**与全量评审无实质差别**。任务数 ≥ 8 尤其无效：其分位数 p25=6、p50=10，阈值卡在中位数附近等于没卡。

既然正向规则做不到有效区分，不如把默认设为评审：判据判错时是「多做一次评审」而不是「漏审」。反向实测：最窄的跳过规则（`fast-track` 且 能力数 ≤ 1）放行 29%，加「交付物 ≤ 3」后放行 10%。

**为何删掉原设想的「交付物路径触及 `core/`」判据**：`core/` 只是本框架自托管时的目录名，被管项目没有这个概念，与「不做项目级特殊处理」的既有原则冲突。同理，「交付物声明条目数」被判据采用但阈值上调（≤ 3 才跳过），因为它受声明规范变更影响，用作跳过条件（保守侧）比用作评审条件（激进侧）安全。

**代价**：评审 run 数量显著高于初始设想。缓解见 D10（单轮只读、成本量级远低于 implementer run）。

### D3 `evo-` 前缀为硬否决项

**决定**：`evo-` 前缀 SPEC 永不命中跳过白名单，即使它同时满足 fast-track、单能力、少交付物。

**理由**：`evo-*` 由框架自动从自省报告提炼、无人工方案背书，是本特性最主要的目标受众。若允许其命中白名单跳过，「批量产出质量保障」的目的就会被同一个批量的特征自我取消。该判据实现为跳过条件中的一个 `and not name.startswith("evo-")`，成本近似为零。

### D4 评审 Agent 复用 `dispute-judge` 判官范式（主树、无 worktree）

**决定**：`run_spec_review()` 对齐 `core/agent_runner/runner.py:run_dispute_judge`——不建 worktree，`cwd` 为主树项目根，`--add-dir <项目根>`。

**理由**：评审者需要读的东西全在主树里——SPEC 三文档、`spec/archive/` 下 154 条已归档 SPEC、`.fenix/runs/` 下每次 Agent run 的流转录。建 worktree 等于把要被评审的对象复制一份到隔离目录，然后让评审者看副本、让修补结果再经 merge-back 回主树，凭空引入一条本框架历史上多次出问题的 merge-back 依赖链（untracked spec 死锁、stash pop 冲突、目录重命名盲区均有事故记录）。判官范式在本仓库已有成熟先例与既有硬门配套。

**代价**：评审者获得主树写权限，需要额外的边界校验（见 D5）。

### D5 主树直改 + 检测式边界校验（而非强制隔离）

**决定**：评审者可写 `spec/changes/<spec>/`；框架用「派发前快照 / 收工后比对」检出越界写入：`repairs` 路径合法性、SPEC 目录外的新增修改、`status` 与改动的一致性。任一越界 → 本轮判定为「未完成」，进重试计数，最终 blocked 并列出越界清单。

**为何是检测而非强制**：框架以 `--permission-mode bypassPermissions` 启动 `claude` 子进程，无法在进程层面限制其写入范围。诚实的设计是承认这一点并做可靠检测，而不是宣称一个不存在的沙箱。

**快照为何要含脏文件内容哈希**：主树常存未提交的人工在途修改，`git status --porcelain` 的前后差集无法检出「某个已脏文件又被改动」——它的状态字符串始终是 ` M`。因此对脏文件追加内容哈希快照。这既准确又廉价（只需遍历已脏文件，不是全仓库）。

**为何不自动回滚越界改动**：快照恢复会把「越界 run 改动」与「人工在途修改」一视同仁地还原，在主树长期存在未提交工作的现实下，误伤人工工作的代价远高于保留一份越界改动。符合本框架「宁可停下叫人」的哲学。

### D6 故障重试后 blocked，且与 `rejected` 严格区分

**决定**：评审 run 未通过硬门/边界校验时**不计入否决**，重试（累计尝试上限 3 次：首次 + 最多 2 次重试），耗尽后转 `blocked`，error 前缀 `spec-review-incomplete:`；评审者主动否决转 `blocked`，error 前缀 `spec-review-rejected:`。

**为何不 fail-open 放行**：若评审失败即放行，则「让评审器崩掉」成为绕过评审的确定捷径，门禁形同虚设。评审是这个 SPEC 进入实现前的最后一道方案关，未知不等于无风险。

**为何重试而非一次定生死**：本框架历史上基础设施抖动（网关长尾、子进程被误杀）造成的「假信号」有多次记录，一次失败即停人会把大量噪声灌进人工队列。

**为何两类 blocked 必须同前缀族但不同值**：两者都停下等人工，但**人工要做的事完全不同**——`rejected` 需要读方案并裁决，`incomplete` 需要看评审器为什么没跑成。Dashboard 与 CLI 靠前缀区分二者（重新评审入口的开放条件即依赖此前缀）。

### D7 评审结论三值 `approved` / `repaired` / `rejected`

**决定**：`approved` = 方案可行且无改动（`repairs` 必为空）；`repaired` = 方案可行且已就地修补（`repairs` 必非空）；`rejected` = 存在方向性风险（`findings` 必含至少一条 `blocking`）。

**理由**：把「已修补」单列一值，使框架能做一致性校验（`approved` 不该伴随文件改动、`repaired` 不该没有修补清单）——这正是 D5 边界校验的判据来源。若合并为一个「通过」值，改动与声明就无从对账。三值也让人在时间轴上直接看到「这条 SPEC 被评审官改过」。

### D8 人工恢复双路径 + 入口的 error 前缀限定

**决定**：新增 `blocked → reviewing`（重新评审）与保留 `blocked → ready`（担责放行）。重新评审入口**仅对 `error` 前缀为 `spec-review-*` 且无 `frozen: true` 的 blocked SPEC 开放**。

**理由**：`blocked` 当前承载熔断、合并失败、人工冻结三类语义，其设计含义是「自动链已停止，唯一出路是人工恢复」。若对任意 blocked 开放 `→ reviewing`，一次误操作就能把因熔断停下的 SPEC 重新推入自动链，破坏熔断的意义。前缀限定把新出口的作用域收敛到「评审引起的 blocked」这一新建子集内。

**冻结保护的双层**：前缀限定是第一层（冻结 SPEC 的 error 为冻结规范前缀）；`update_spec` 既有的「冻结期剥离对 `status` 的改写」机制是第二层兜底，即使第一层被绕过也无法移动冻结 SPEC。

### D9 `reviewing` 为中断态，daemon 重启回退 `drafted`

**决定**：与 `implementing` / `testing` 同口径——daemon 重启把 `reviewing` 回退 `drafted`，清空评审 run 引用与尝试计数，重走晋升链（软化与两道 lint 幂等，分流重判）。

**理由**：回退到链首而非「保持 `reviewing` 并重派」有两个好处：语义单一（每条 SPEC 只需要一条恢复路径）、幂等收敛（软化与 lint 本就设计为可重复执行）。若评审者已改过 SPEC 后崩溃，重跑会基于**已修补的内容**再评一次——评审者看到的是改进后的方案，结果只会更好，不会打转。

### D10 结果硬门与 run 元数据全复用既有机制

**决定**：评审结果走既有 `_check_agent_result_artifact` 硬门（exit 0 + 文件存在非空 + 合法 JSON + 顶层对象 + `status` 白名单 + mtime 新鲜度）；run_id 前缀 `spec-review-` 同时登记在 `core/agent_runner/run_files.py` 与 `core/admin_monitor.py` 两处前缀元组；模型经既有 `agents.models` 结构路由。

**理由**：这三样都是本框架踩过坑后固化的机制——硬门的 mtime 新鲜度校验专防「陈旧合法文件替本轮放行」（有历史事故），`_RUN_PREFIXES` 两处同源是既有约束（两处不同步会导致 run 文件与监控口径分裂）。复用即继承这些防护。评审单轮只读、不跑测试、不写代码，单次成本量级远低于 implementer run，这是 D2 敢选「默认全量」的成本前提。

### D11 配置面最小化

**决定**：只新增两个键——`gates.spec_review_mode`（`auto`/`never`）与 `agents.models.spec-review`。跳过判据、重试上限、结果目录路径一律硬编码。

**理由**：本框架有「新增配置项必须带 Dashboard 界面」的硬性约定，每个键都要配设置页控件、受管键白名单、热更新、文档与测试。跳过判据是个启发式，给它四个阈值旋钮既让界面臃肿，又给使用者一种「调参就能调准」的错觉——而 D2 的实测已表明静态特征在这个维度上区分力有限。`never` 提供了整体关闭的逃生门，这已足够。

## Risks / Trade-offs

**[主树写入无法硬阻止]** → 只能检测不能强制（D5）。缓解：快照检测覆盖三类越界形态；检出即停人并列出清单，绝不静默放行；不自动回滚以免误伤人工在途修改。

**[评审本身是 LLM 判断，可能误判]** → `rejected` 一律交人工，不自动删除或改写方案；输出含 `confidence` 字段供人工快速分诊；提示词要求 `evidence` 必须引用具体文件路径与位置，禁止无依据断言。

**[评审成为调度瓶颈]** → 评审 run 计入既有并发闸门（不新开通道），并发满时 `reviewing` SPEC 排队等待而非跳过评审。评审单轮只读，耗时量级低于实现 run。

**[新状态触及面广，可能漏改某处状态全集消费点]** → `VALID_TRANSITIONS` 之外，需复核所有遍历 `SpecStatus.ALL` 的位置（Dashboard 状态色板/筛选、文档、任何状态穷举分支）。缓解：tasks 中单列一项「状态全集消费点普查」任务。

**[默认全量评审抬升自进化成本]** → `evo-` 批量产出每条都过评审。缓解：这是本特性的**目的**而非副作用（D3）；`gates.spec_review_mode: never` 可整体关闭；评审成本单轮只读，远低于其挡下的那轮实现+验证。

**[分流判据依赖后成规范的字段]** → `mode` 与 Deliverables 声明段在存量 SPEC 中可能缺失（`spec/archive/` 154 条中 113 条两者皆无）。缓解：判据设计为「缺失即保守取不跳过」（缺失 → 进入评审），使规则在旧形态 SPEC 上失效时偏向多评审而非漏审。

**[评审者越界修补 SPEC 反而引入错误]** → 评审者可能改错。缓解：`repaired` 的改动留在 git 工作区，人工可经 `git diff` 审计；评审者只能动 SPEC 目录，无法触及实现代码；`rejected` 路径保留人工裁决作为兜底。

## Migration Plan

1. **配置**：`gates.spec_review_mode` 缺省 `auto` 即生效，无需迁移；不配置即启用默认全量评审。需回退时设为 `never`，四条通道立即恢复旧行为（`drafted → ready` 直通），无需重启（30s 热更新）。
2. **存量 SPEC**：无迁移动作。处于 `drafted` 的 SPEC 在下一次触发时按新链流转；已处于 `ready` 及之后状态的 SPEC 完全不受影响（评审门只在 `drafted → ready` 之间存在）。
3. **daemon 重启**：若升级时恰有 SPEC 处于 `reviewing`（仅在升级前后极短窗口内可能），重启的既有中断态回退逻辑会把它送回 `drafted`，重走新链——收敛，无需手工干预。
4. **回滚**：把 `gates.spec_review_mode` 设为 `never` 即停用新行为。代码层回滚需注意：若回滚时有 SPEC 停留在 `reviewing`，旧代码不认识该状态，需手工把这些 SPEC 改回 `drafted`（或先置 `never` 让它们在链内推进完毕再回滚）。

## Open Questions

1. **重试上限取值**：当前定为累计 3 次尝试（首次 + 最多 2 次重试）。若实际运行中基础设施抖动导致的 `spec-review-incomplete:` 过多，可考虑上调；反之若人工队列被噪声灌满，可下调至 2 次尝试。实现时硬编码为常量，便于后续提升为配置键。
2. **跳过白名单阈值是否需长期可调**：当前硬编码 `能力数 ≤ 1 且 声明条目 ≤ 3`。若实际运行中跳过比例明显偏离实测的 ~10%，说明判据需要重新校准——届时应先补实测数据再决定是否加配置键，而非直接开旋钮。
3. **`repaired` 是否需要在 Dashboard 时间轴上单列节点**：评审者改动 SPEC 是一类值得留痕的事件。当前设计只通过 `git diff` 与结果 JSON 可查，未做专门的时间轴节点。若人工需要更强的可追溯性，可后续追加。
