# 提案：重开 D5——tracked 流散件注册表落盘与同指纹静默窗

## 背景与动机
dsh-plugins 主树一枚人工散件（panels.tsx，2026-11-17 起字节级零演进）触发 maintree_stray_wip_stale 盘点告警第 22-28 度七连复发：本窗 4 次 daemon 重启后 69-71 秒内必重登记 first_seen（4/4 命中），30 分钟宽限耗尽即重告，7 轮 administrator 处置 run 空烧 1245 秒/5.70 美元；上窗同型 7 run 6.12 美元——两窗 14 次 11.8 美元，另加 14 枚零新信息知识回写 commit。根因是 D5 设计决策把 tracked 流 first_seen 注册表留在进程内存态（stray_wip.py:22-33「损失仅时效」，:511-518 重申），重启即重置宽限；且存活期同指纹无静默窗（25/26 度以 37/35 分钟周期逐轮重告）。该决策在「损失仅时效」假设下成立，但两窗实测损失是完整处置 run 烧钱加重复升级提请，假设已被实证推翻。

## 目标
1. tracked 流 first_seen 注册表同构落盘 .fenix 运行时状态区（复用 evo-persist-stray-escalation-clock 为 untracked 流落地的字段白名单/加载/原子写先例），重启后宽限与升级时钟连续。
2. 加同指纹静默窗（24 小时滚动冷却）：同一改动指纹（路径排序集 + `git diff HEAD` 内容哈希，同指纹即 diff 字节级零演进）距上次告警不足 24 小时不重告、仅累计抑制轮数；满 24 小时可再发一条并附累计度数。指纹演进（新指纹）按常规宽限正常告警。静默窗台账独立于计时条目生命周期——归因/持有者分支 pop 计时条目不得清空静默窗。

## 非目标
- 不改处置口径本体（零触碰+知识页回写+升级提请）——处置面已在知识页 stray-wip-disposal 蒸馏至第 28 度。
- 不动 untracked 流既有落盘与白名单语义。
- 不改盘点周期本身；人工侧三选一收口（worktree 车道/明示认领/豁免盘点）属流程动作不在本 SPEC。
