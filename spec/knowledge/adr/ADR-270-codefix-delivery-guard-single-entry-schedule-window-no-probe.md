# ADR-270：code-fix 投递守卫唯一入口收敛，周期断窗静默窗规避不探测

date: 2026-10-13
status: accepted

## Context

code-fix 批激活有四路触发——批收尾自驱动 _resubmit、审查收尾新条目激活、event_bus full-scan 兜底、持有者终态回调——全部汇入 `CodeFixOrchestrator.checkpoint()` 这一唯一共用投递入口。上游链路存在每日固定时刻断窗（两块物理独立网卡同秒 Lost carrier、逐日同刻复发），批次恰在窗中启动即 api_timeout 终局，每夜损失一个在跑 run 加约半小时冷却推迟。需要在投递路径上拦住「启动进已知断窗」：判定逻辑放四路触发点分散实现还是收口单点、是否引入对上游可用性的主动探测作为替代防线，需要裁定。

## Decision

- 投递守卫一律收敛在 checkpoint() 公共路径单点判定，不在触发点分散实现；任何新增激活路径必须经 checkpoint() 汇入，以测试固定该不变量，不得旁路。
- 公共路径守卫对手动触发同样生效：`override_enabled=True` 手动授权只越过 enabled 总开关，不越过公共守卫（沿 ADR-180 手动触发保留守卫链契约）。
- 对已知周期性断窗采用配置化时刻静默窗做时间维度的前置规避（窗内拒新批、窗末自动放行、按窗次幂等的武装/解除留痕），不引入对上游可用性的主动探测；窗口外的连接类瞬态仍由冷却与 api_timeout salvage 事后防线兜底。

## Consequences

- 守卫语义天然全覆盖、无双写不一致；代价是 checkpoint() 成为车道投递的关键汇聚点，新增触发路若绕过它将静默失去全部公共守卫，只能靠不变量测试拦截。
- 静默窗按时刻表规避、不感知上游真实状态：窗口消失后退化为每晚固定约 30 分钟不投递，武装/解除留痕使其显性可见，配置可一键关闭；在跑长批横跨窗口的死亡不在本防线内，由 api_timeout salvage 兜底。
