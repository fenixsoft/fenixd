# ADR-354：Arbiter 处置动作面黑名单制与禁项单源机械门

date: 2026-11-12
status: accepted

## Context

Arbiter 车道原处置模型为「白名单+判定反例」（宁可升级人工）。台账复盘实锤：多数升级件落在机械可判域且人工均可救回（场景鲁棒性修复、稳态复跑），部分判定反例（如「改断言=MUST escalate」）方向性错误；同时提示词级红线存在被模型漂移突破的既有教训（judge 写回受理门同源）。处置哲学需要反转，且反转后的边界必须落在机器可校验的载体上。

## Decision

Arbiter 处置动作面以黑名单治理：禁项外一律默认可救，判定焦点由「是否在许可清单内」反转为「是否命中禁项」。禁项（B1–B5：生产账本副作用/人工裁决通道代行/破坏性动作直执/验证契约放宽/越界写）以 python 模块单源（`core/pm_engine/arbiter_blacklist.py`），prompt 禁项文案由同一模块导出注入——文案与谓词同源。机械门为唯一防线，prompt 只引导。拒绝 yaml 配置（禁项谓词需要代码表达力：生产端点族清单、写路径判定、报告字段扫描）与 prompt/谓词双源（漂移风险）。命名消歧：本模块为处置动作面禁项，与链级触发面黑名单 `chain.blacklist`（信号入链过滤 kill switch）不同层、互不冲突。

## Consequences

后续 Arbiter 处置能力扩展（新增可救工具或新增禁项）在单源模块内演进，禁止另立第二禁项枚举或 prompt 侧私改文案；处置深度由许可清单枚举变为禁项边界+机械门，机械门误判面由保守分类与守卫测试约束；模型行为漂移不再依赖提示词约束兜底。后续其他 agent 车道若需要同类「默认可救+枚举禁项」边界，沿用本裁定形态（代码单源+文案同源导出）。
