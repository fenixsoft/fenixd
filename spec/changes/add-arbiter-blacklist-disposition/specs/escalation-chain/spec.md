# escalation-chain Specification

## ADDED Requirements

### Requirement: 早期介入路由（验证失败同签名复现）

升级链 SHALL 支持加性早期触发面：同一 spec 的验证失败签名（失败场景集指纹单源）连续 ≥2 轮复现时，在预算耗尽/冻结发生前直接路由 Arbiter 车道（Admin 车道跳过——验证域修复非 Admin 拍板面）。触发为加性：既有预算耗尽→冻结→链升级路径行为零变化，早期触发与冻结路径互不取代（先到先得，另一方命中时去重合并）。早期触发受既有配额治理（`arbiter_rulings` 3 次/签名——对齐单源现值 `CHAIN_ARBITER_RULINGS_DEFAULT=3`，2026-11-03 定调 2→3、复位窗不变）与本能力救回防抖约束，dead-man 语义不适用（验证失败非 dead-man 类）。路由载荷 SHALL 携带失败签名、逐轮失败面对照与 judge 归因摘要（如有），供 Arbiter 直接选用救回工具箱。

#### Scenario: 同签名两轮早期路由

- **WHEN** 某 spec 验证失败签名连续 2 轮复现且未触发预算耗尽冻结
- **THEN** 链直接路由 Arbiter（跳过 Admin），载荷含签名与逐轮失败面对照

#### Scenario: 与冻结路径去重不双派

- **WHEN** 早期触发已派发同签名 Arbiter 调查且该 spec 随后因预算耗尽冻结进入链升级
- **THEN** 链去重不重复派发（同签名在飞/已处置按既有签名治理合并），人工不收重复告警

#### Scenario: 冻结路径行为零变化

- **WHEN** 验证失败仅 1 轮或签名逐轮变化（非同签名复现）
- **THEN** 不触发早期路由，既有预算耗尽→冻结→链升级路径逐字节一致

### Requirement: 救回防抖

同签名救回失败后（Arbiter 处置终态 escalate 或硬门降级），签名状态 SHALL 记录救回指纹（失败场景集指纹+处置轮次）；同指纹再次触发 MUST NOT 重派 Arbiter（按既有复现配额上升路径直达人工），直到签名发生变化（失败场景集、断言集或失败指纹与上次救回时不同）方重新获得 Arbiter 派发资格。防抖状态随既有复位窗语义清零（7 天无复现或 spec 状态迁移）。

#### Scenario: 同指纹不重派

- **WHEN** Arbiter 对签名 S 救回失败（escalate）后，完全相同的失败指纹再次触发
- **THEN** 不重派 Arbiter，按既有配额/上升路径直达人工，台账记录防抖命中

#### Scenario: 签名变化重获资格

- **WHEN** 救回失败后失败面发生变化（新失败场景或新断言集，指纹不同）
- **THEN** 视为新签名问题，Arbiter 派发资格恢复，配额按新签名计数

#### Scenario: 防抖状态随复位窗清零

- **WHEN** 签名连续 7 天无复现（或 spec 状态迁移）后同签名再次触发
- **THEN** 救回指纹与配额一并从 0 计数，Arbiter 可再次派发
