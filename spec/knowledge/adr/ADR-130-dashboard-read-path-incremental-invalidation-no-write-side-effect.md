# ADR-130：dashboard 读路径增量失效、签名完备与读侧零写副作用

date: 2026-09-21
status: accepted

## Context

读路径成本随数据量二次方衰减：聚合索引在 STATE 签名变化时丢弃全部缓存并逐 spec 重扫 run 目录（冷重建秒级），单请求含数万次 JSON 解析；run 目录清理键失效致无界增长。若只保留索引、仍按文件签名比对失效，会出现「STATE 条目字段变了但依赖文件没变」的条目永远返回陈旧摘要（预算闸门/冻结把 spec 置 blocked 时，tasks.md 等文件均未变）——这正是增量缓存要避免的陈旧读，只是来源从 TTL 换成了签名不完整。

## Decision

- 读侧缓存采用**增量失效**：签名变化时保留旧索引，按 spec 自身签名逐条判失效、只重算变化项；全量重建只留给冷启动与索引损坏。否决加大 TTL——会读到陈旧数据。
- 缓存签名必须**完备覆盖决定输出的全部输入**：除依赖文件签名外，还必须把 STATE 条目自身的关键字段（状态、优先级、错误、锚点、冻结位、计数类字段）序列化为稳定指纹并入签名；判据是「宁多勿漏」，增量失效的正确性以「增量结果 ≡ 全量重建」等价性用例为验收门。
- run 文件读取用尾读 seek + `(path, mtime_ns, size)` 元数据 memo：append-only 文件未变即零读；尾读窗口不足或末行超窗时回退全量逐行读，**末行超长不得从中间截断**（曾致已完成 run 被误判 running）。否决持久化文件索引——复杂度与失效管理不值当。
- **读侧零写副作用**：清理/归档类写操作挂 daemon 周期任务，不挂在读路径（watcher 是读侧，不应有写副作用）。

## Consequences

- 读成本从 O(specs × runs) 降为 O(变更量)，单请求延迟回到百毫秒量级；run 目录按上限受控。
- 任何向读路径新增数据源的后续变更，必须同步扩展对应签名并补等价性用例，否则即是陈旧读缺陷。
