# ADR-241：归档条目迁出「先清单后活跃」顺序不变量，STATE 活跃集 + 归档清单双真源

date: 2026-10-06
status: accepted

## Context

`.fenix/STATE.md` 条目只增不减（三条归档路径都只移目录），写侧每次状态流转/预算自增全量重写整文件，写放大随条目数线性恶化。既有「已归档」可见性以条目永久保留为前提（ADR-056：目录存在性唯一事实源），直接迁出条目会使判定失效；而迁出「删活跃 + 写清单」两步之间存在崩溃窗口，若顺序不当会产生「活跃已删 + 清单没有」的丢条目态——STATE.md 是全框架单一状态真相源，丢条目即丢 SPEC 簿记。evo 撞名检查、软删除 found 判定等读侧消费方各自只读活跃源，迁出后不收口会出现口径分裂。

## Decision

1. STATE.md 收敛为活跃条目集合，归档清单 `.fenix/STATE.archive.md`（与 STATE.md 同格式、共用解析）作为已迁出条目的唯一居所。已归档判定改为双源合取：活跃目录不存在 ∧（活跃 STATE.md 或 归档清单 有条目）——对 ADR-056 的「目录存在性唯一事实源」收窄为合取项之一，其「不写 STATE 标志」原则保持（条目是迁走，不是加标志）。
2. 迁出原语在 STATE.md 既有 flock 锁内固定「先清单后活跃」顺序：先把条目（含 archived_at/archived_by）追加写入清单（单次 write + fsync），再重写 STATE.md。崩溃窗口只允许出现「清单已有 + 活跃仍有」的双源中间态（读侧活跃优先、回填下轮收敛），绝不允许出现「活跃已删 + 清单没有」的丢条目态；清单写入失败时 STATE.md 不动、条目不丢。
3. 三条归档路径收口同一迁出原语；读侧消费方（spec 列表、evo 撞名去重、软删除 found 判定）一律双源口径且活跃侧优先；统计（overview/project_summary）恒活跃口径，不并入清单。清单只经迁出追加、同名幂等覆盖、软删除移除三类写操作，活跃状态流转不得触碰清单。

## Consequences

后续新增的 STATE 条目读侧消费点必须接入双源合取（漏接即出现「已归档却不可见/可撞名」缺口）；读侧不得假设两源互斥——双源并存是设计内中间态（最坏停留一轮周期），同名冲突恒活跃侧优先。清单为终态快照、写入频率等于归档频率，覆盖式去重的整体重写成本可接受；代价是清单整体重写与活跃重写共持一把锁，归档批量回填期间状态流转短暂排队。回填挂既有低频周期且不受阈值开关约束，是双源收敛的兜底机制，禁移除。
