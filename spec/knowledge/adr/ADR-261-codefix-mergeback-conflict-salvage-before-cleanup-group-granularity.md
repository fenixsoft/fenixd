# ADR-261：code-fix 合回冲突救回挂即弃前单轮闭环、组粒度回收禁无据归属

date: 2026-10-09
status: accepted

## Context

code-fix 批回归跑在 worktree 上、看不见 main 新提交，链生命周期内基线前移引入的语义冲突在批末合回预演（merge-tree 预演闸）才首次暴露，按既有设计整批现场即弃——约 1 小时批处理算力双倍消耗，同型事故反复复发（五次实证）。即弃后分支被删、worktree 被回收，tip_sha 仅 GC 前可用，事后无任何救回杠杆；而实测同批 14 提交中仅 1 个触碰冲突文件，13/14 的修复成果与冲突无关却陪葬。

## Decision

- 救回插入在即弃分支内、`_safe_cleanup` 之前，单轮闭环，不依赖分支/worktree/tip_sha 跨轮存活；救回形态为解析当前基线 → 批分支 rebase → 重跑批回归 → 重走合回，至多尝试 1 次。
- 救回失败降级 commit 组粒度 cherry-pick 回收：以提交是否触碰预演冲突文件集（`MergeConflictInfo` 单源）判定可回收，回收集重跑批回归后重走合回；仍冲突组对应条目入失败档案计 fail_count 走既有预算；终局兜底仍是整批入档，行为与无救回时兼容。
- 条目归属以提交 body `items:` 清单为唯一依据（commit 契约的结构化标注）；解析不出清单的旧契约批保守整体入档——禁无据归属，条目级精确回收假设不被采纳。
- wip_gate_blocked（主树 WIP 预检阻断）的 defer 零预算路径不触发救回、语义不变；救回重走合回命中该阻断同样按 defer 零预算处理，不计救回失败。

## Consequences

- 真冲突场景下非冲突修复成果不再陪葬，链不再 resolved=0 全弃，冲突即弃链的重复算力消耗随救回成功率下降；救回失败最坏退化为现状（整批入档 + 预算重试），无新增损失面。
- 救回 MUST NOT 移出 cleanup 前窗口——rebase/cherry-pick 改写批分支历史的安全性以「分支独立且尚未合回」为前提，跨轮存活类设计（依赖 tip_sha 或分支引用延续）被排除；后续触碰归属解析者不得引入无据归属，触碰救回时序者不得削弱单轮闭环约束。
