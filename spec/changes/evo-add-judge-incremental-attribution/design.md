# 设计：judge 归因增量落盘

## Context

planner-judge 归因查重（fenix-server 09-10 窗口新增能力，fenixd.log 15:53:16Z/16:39:41Z 实证 add-web-ui）是整批判定：judge 一次性产出全部场景归因，查重门按整批接受/废弃。单轮 $10+ 大产出被整体废弃（planner-judge-add-web-ui-1789056218-a1 cost=11.155171），重跑保留再产出模板化归因的风险——错误成本回收无机制。

## Goals / Non-Goals

- **Goals**：归因按场景独立落盘；查重拒绝按场景子集回炉，已通过场景复用；防御语义不弱化（全量重复仍整批回炉+告警）。
- **Non-Goals**：不改查重算法本身（n-gram 相似语义保留）；不做部分通过自动合并（回炉后仍需完整查重判定）；不改统计 schema 层 UI。

## Decisions

### D1：增量条目落在同一产物文件内，不新建目录

**选择**：同轮 judge 产物仍是一个文件，但内部按 `scenarios: [{id, attribution, status}, ...]` 逐场景条目组织；旧整块结构读侧兼容。

**理由**：最小文件面变化、易审计（一轮一文件）、读侧兼容；独立文件方案增加文件面管理成本，收益不显著。

### D2：回炉状态机为 requeued ↔ accepted 双态 + 终态聚合

**选择**：每场景条目带状态：accept / requeue；查重命中置 requeue，其余 accept 保留；requeue 子集汇总为回炉清单驱动下轮 judge 只重做该子集，完成后整轮再校验。

**理由**：状态机简单可测；「只重做子集」达成后仍需整批校验一次防交叉污染，但回炉输入规模大幅缩小。

### D3：全量重复不改告警面

**选择**：场景级拒接后，若回炉子集=全量（100% 重复），复用既有整批拒绝的 escalation 告警（src 语义同 '批量归因查重拒绝'）。

**理由**：查重防御本意（拦模板化归因）必须保持；只有部分重复时静默回炉子集。
