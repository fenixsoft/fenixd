# ADR-285：todo.md 标记提交去抖按生产者批末收集，禁建跨生产者文件级合并窗口

date: 2026-10-27
status: accepted

## Context

自进化标记回写的接受路径逐条即时提交，按「每轮分析有接受条目」复现提交风暴（potplayer-base 两秒 8 提交、fenixd 仓三连/七连），单批敞口上限 `self_evolution.max_items_per_run=20`。批末单次提交的机制（commit_todo_marker）与范式（ingest 侧、maintenance_runs 批末段）均已存在，缺的只是接到接受循环。备选「1-2 秒文件级合并窗口」看似能一并吸收所有生产者的滞留改动，但 `.fenix/todo.md` 有两个生产者——evolution 与 self_review 的 `_commit_todo`——以同 pathspec（`git commit -- .fenix/todo.md`）不同消息提交，时间窗去抖会把对方滞留改动卷进错误消息的提交并随 push 外泄（实害，非理论风险）。

## Decision

提交合并只按生产者批内收集：每个批处理消费方（ingest 落库、自动接受循环、保留清理）在自己的循环内逐条写标记不提交、批末对本批涉及的每个项目各调一次合并提交，作用面限于该循环自己的写入；不引入任何文件级/时间窗的去抖合并。单点写路径（dashboard 手动单条接受、拒绝、手动单条删除）保持写后即提交；批去抖经显式 defer 开关声明，缺省即时提交不变——存量「单点写写后即提交」决策对单点面继续成立，只有批循环消费方显式让渡。合并提交丢失逐条边界由消息正文附条目 id 明细补偿，git 历史仍可对账到条目。后续新增的 todo.md 批量写消费方同型接入（defer + 批末按项目各一次），禁止以时间窗吸收其他生产者的改动。

## Consequences

- 接受批的标记提交数从 O(条目数) 降为 O(涉及项目数)，提交风暴消除；SPEC 立项提交（spec 目录 pathspec）属立项语义不在合并面内，仍逐条一次。
- 批中途中断（daemon 被杀）时已写标记未提交：todo.md 状态与 git 提交解耦、下轮扫描以文件为准，与 ingest 侧同窗口，既有恢复/盘点流程覆盖，不为此加提交前持久化。
- 合并提交消息随条目数线性变长，可接受；跨生产者污染面保持为零的代价是同刻多生产者各自产生一枚提交，提交数不追求全局最小。
- 无变更批末提交以良性 no-op 收敛（INFO 不告警），不视为失败。
