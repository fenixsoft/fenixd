# ADR-377：SPEC 软删除↔告警一致性联动挂删除原语单点、fail-open 独立错误键

date: 2026-11-17
status: accepted

## Context

SPEC 经软删除后，引用它的未处理告警（如 spec-review-rejected）成为悬空条目：告警推荐的 abandon 此后永远失败（`spec not found`），用户无法经告警完成收口，告警与 spec 真实状态脱钩。既有闭环机制 `alert_lifecycle` 为周期扫描式（signal_type 条件注册表白名单），「spec 从状态表消失」不构成任何在册条件的解除证据——缺口属事件式联动，结构性不在扫描通道职责内。软删除有两条调用通道（SPEC 管理删除端点、裁决 abandon 执行器）共用同一底层 `soft_delete_spec`。

## Decision

1. **联动挂在 `soft_delete_spec` 删除原语内部，不在各调用方各自实现、不扩展扫描条件注册表**：删除语义与「主体消失→关联告警失效」是原子因果，双调用方天然同治，未来新增软删除调用方自动继承联动。写回经 AdminStore 排他锁独立路径，`handled_by` 取独立值 `spec-softdeleted`，不复用 `auto-resolve`——后者语义绑定「周期扫描 + 条件注册表 + trigger 前提」，删除事件驱动无 trigger，独立署名保证审计可辨（与 auto-self-heal / superseded 各自独立取值同范式）。
2. **联动为删除本体 best-effort fail-open 后置步骤，失败说明落独立字段、MUST NOT 占用顶层 `error` 键**：删除本体已发生（目录已迁移），告警写回失败反向回滚会造成更大状态分裂；返回对象顶层 `error` 是删除本体的既有失败语义键（abandon 执行器据其判成功分类、删除端点据其报失败），被联动失败占用会把已成功的删除对两个调用方反转成失败，重造本裁定要消除的脱钩。
3. **存量悬空告警的收口出口走 abandon 幂等化**：`found=False`（活跃 STATE 与归档清单双查均无）判幂等成功而非失败——目标态「spec 已不存在」已达成；不引入「spec/changes 目录残片仍存在则失败」的第三态判断，状态表为唯一真相源。
4. **`archive_spec` 归档通道暂不联动**：归档面向完成态 spec，其告警通常已随终态收口；是否同治属独立产品决策，不做隐式扩展。

## Consequences

删除事件与告警台账在单次操作内一致，悬空告警类别性消除；新增软删除调用方零成本继承联动；独立 `handled_by` 使删除事件驱动的收口在审计上与扫描自动闭环可辨。代价：告警写回失败时删除照常成功、告警暂存悬空（失败说明留返回对象独立字段与 WARNING 留痕，待人工或重试收口）；归档通道是否同治须独立 SPEC 裁定，本裁定不预授权扩展。
