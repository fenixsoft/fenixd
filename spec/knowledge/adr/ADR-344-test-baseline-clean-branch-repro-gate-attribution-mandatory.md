# ADR-344：测试基线修复走干净分支复现门与归因强制

date: 2026-11-10
status: accepted

## Context

主线全量测试基线 2026-11-10 两次实测失败数漂移（12 failed → 11 failed），11 项存量失败跨 7 簇（salvage 链、declaration 解析、fake-double 测试债、logger 旁路、push ref hygiene 等）；工作树含并发 SPEC 的 dashboard WIP，失败集合两次不一致说明存在 WIP/环境诱发面。逐项盲修的风险：把并发 WIP 诱发的伪失败当真实回归修（引入无谓改动甚至真缺陷）；以删测试/放宽守卫清零的风险：基线变绿但缺陷被掩盖，依赖「全绿验收」口径的后续 SPEC（平台抽象层 SPEC-1）建立在假基线上。

## Decision

存量测试失败的处置一律过四道纪律：(1) 干净分支复现门——先在从 HEAD 切出的干净实现分支上单测节点级复现，复现才动手，不复现记 `[WIP]`/`[隔离]` 归因关闭、不改任何代码；(2) 归因强制四类（`[违例]` 修实现 / `[断言]` 修断言并注明「断言脱节」复核证据 / `[隔离]` 修隔离确定性 / `[WIP]` 关闭），归因与证据落处置任务说明；(3) 反掩盖不变量——禁止删测试、放宽守卫、无归因改断言清零，守卫测试本体与白名单不动，真实违例修实现；(4) 同簇失败先收敛共同根因再修，禁止逐测试打补丁。基线验收以有界入口 `bin/run_full_suite.py` 间隔两轮全量 0 failed 为准；该纪律同样适用于基线外新失败。

## Consequences

- 2026-11-10 基线 11 项失败仅 2 项真实修复（13 处替身签名显式化 + 1 处日志层级名），9 项 WIP 归因关闭、零代码改动——复现门避免了 9 项无谓修复及其潜在掩盖。
- 代价：每轮基线处置多付一次干净分支复现与双轮全量（单轮约 12 分钟）的时间成本；并发会话期间的全量基线数字不具权威性，跨 SPEC 并发时点不得据其立项修复。
- 「全量 0 failed」成为声明全绿验收口径的后续 SPEC 的成立前提；新失败沿用同款纪律，基线契约长期成立（能力页 `legacy-test-baseline-green`）。
