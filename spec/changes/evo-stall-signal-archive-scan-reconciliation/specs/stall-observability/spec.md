# 能力规格：stall-observability（API 停滞信号观测）

## 概述

run 级与车道级 API 停滞信号的入账与触发规范：保证任何终态 run（无论是否已被保留清理归档）的停滞计量都能进入日累计与单轮升级判定，且累计面具备对账自证能力。

## 需求

### R1 扫描面含归档

停滞信号面的 run 档案扫描必须覆盖 runs 目录顶层与 archive/：终态 run 被保留清理移入归档后，其停滞行仍可被后续巡检轮入账；「终态落盘→归档」窗口窄于巡检节拍时不得造成信号漏报。

### R2 对账自证

每巡检轮（或每日一次）将终态 run_metrics 停滞行合计（含当日 archive 内终态 run）与内存累计器对账：差额超过阈值（建议 60 秒，即单条记账线）时补发 lane_stall_daily_budget 信号留痕并注明对账来源。对账自证不得依赖对漏报根因的裁定，作为确定性兜底独立于扫描面修复生效。

### R3 入账去重

同一 run 的同一停滞行不得因扫描面扩展或对账补发而重复入账；去重键沿用既有 run 级去重集合，跨扫描来源（顶层/归档/对账）保持一致。

### R4 既有语义不变

停滞阈值（单轮记账 60 秒、升级 300 秒、车道日预算 30 分钟）、success 终态豁免、UTC 日桶收拢、信号 kind 与 evidence 结构均保持不变。

## 验收标准

1. 构造停滞 run 档案直接落入 archive/（顶层无文件）触发巡检：车道日累计入账且越过预算线时信号落账。
2. 构造「终态落盘后立即归档」场景：下一巡检轮仍能入账，不漏报。
3. 构造累计器与档案合计差额超阈值场景：对账补发信号且 evidence 注明对账来源。
4. 同一 run 档案在顶层扫描、归档扫描、对账补发三种来源下只入账一次。
5. 既有停滞信号测试全部通过，阈值与豁免语义无回归。
