# ADR-318：场景修订通道受理预检 fail-closed 整批拒收，与产出收编剔除继续有意分化

date: 2026-11-03
status: accepted

## Context

场景集写入端的结构校验门（ADR-093）对收编取「坏条目剔除继续、不整批拒绝」语义，适配 planner 产出收编：产出面大、剔除留痕可接受。judge 原地修复走同一受理链路时该语义暴露结构性缺陷：修复是预算受限的修订通道（上限 2 轮），带病采纳把词表违规等机械可判错误推迟到验收期场景执行才暴露（实测潜伏 2 轮，连带烧掉 impl 修复轮与 admin 处置轮）；且「坏条目剔除 + 备份停留旧集」造成成对撕裂，后续无理由缺场景回补把旧定义复辟（端口漂移潜伏复发），而 judge 始终收到修复成功的申报语境。

## Decision

judge 场景修复的受理点（`scenario-repaired` 申报采纳前）挂 fail-closed 整批预检：与唯一结构化写端同源校验（`validate_scenario_dicts`，含 per-kind 词表），任一条非法即整体拒收本轮修复——error 逐条清单留痕、rejected 记账、返回已消费不穿透调用方守卫、消耗既有修复预算不新增轮次；预检通过后受理采纳按成对纪律同覆盖主文件与备份（同版本戳、先 `_scenarios_full.json` 后 `test_scenarios.json`）。通道语义有意分化并约束后续实现：修订/修复类通道（预算受限、带病采纳=把问题推迟到验收期）一律 fail-closed 受理预检 + 成对落盘 + 错误清单重修；产出收编通道（ADR-093 语义）维持剔除继续。语义级错误（端口/URL 客观错误、断言弱化、选择器失配等非机械可判违规）不在预检能力内，仍由验收期执行兜底。

## Consequences

- 机械可判违规在受理瞬间拦截，中间轮次不再白烧；代价是 judge 反复产出非法集会空烧修复预算——由 2 轮上限 + 耗尽两态处置（排程重验 → 升级人工）兜底，拒收记账字段供告警取数。
- 同一冻结收编函数在两类通道下前置语义不同（预检 fail-closed vs 剔除继续），报错文案各自单源，读代码需分辨通道归属。
- ADR-093 的收编剔除继续语义保留不被取代；若未来要把产出收编也改为整批拒绝，须显式 supersede 本裁定并复核 planner 收编路径的误拦面。
