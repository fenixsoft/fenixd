# proposal：关键路径执行前陈旧代码预检

## 问题

daemon 的代码热装载依赖「磁盘代码比进程新且连续空闲 300 秒」的陈旧自愈（stale-code self-heal）。夜间 evo 收尾与归档高峰把空闲窗挤到数小时之后，期间所有车道按旧代码执行。2026-10-11 窗口实测：4 个框架修复 SPEC 于 01:16–01:38 合并主树，代码直到 03:33:00 才装载（时差 2 小时 16 分），窗内发生两起实害：

1. 5 对 verification-report 收尾双提交（01:42–03:27），全部由「单提交收尾」修复要治理的旧代码执行——第一对恰是该修复自己的收尾；
2. 蒸馏批次 03:32:11 在装载前 49 秒派发，被对蒸馏全盲的旧代码击杀，产物（1 知识页 + 2 索引）滞留主树 21 小时以上。

历史检测→装载配对显示：三周 70 次配对中时差≥2 小时 12 次、≥4 小时 8 次、最长 22.05 小时；09-24 已有记载在案的同根实害（spec/archive/2026-10-03-evo-add-stale-code-dangling-deadline/proposal.md：修复悬空 2.8 小时期间实际复发撞名故障）。既有「悬空超时强制重启」兜底现配 8 小时（.fenix/config.yaml:323），2 小时级窗口不受保护。

## 目标

关键路径（verification-report 收尾提交、知识蒸馏派发、admin 车道处置 choice 执行）执行前检查进程代码陈旧旗标（_code_stale，每 30 秒重算、当前仅自愈与告警消费）；发现陈旧即记 WARNING 并写入 .fenix/restart_request 借既有 supervisor 通道（每 2 秒轮询、生产已消费 351 次）加速重启，把修复装载延迟从小时级压到分钟级，消除上述两类复发敞口的公共根因。

## 非目标

- 不改变陈旧自愈既有触发逻辑（空闲阈值触发、悬空超时强转、告警分级均不动）；
- 不做代码热装载（不引入运行中 reload）；
- 不阻塞关键路径动作本身（预检发现陈旧后当前动作照常完成，重启由 supervisor 通道异步进行）。
