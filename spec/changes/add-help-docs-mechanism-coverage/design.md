## Context

姊妹 SPEC `fix-help-docs-contra-behavior`（P0）负责把「说错的改对」；本 SPEC 负责把「没说的补上」（P1 约 26 项机制 + P2 结构校准）。素材来源为 2026-09-26 审计报告：5 个领域代理取证（code-fix 车道、code-review/质量门禁、验证链/裁决、Dashboard 前端、生命周期/守护）+ 主会话自证（状态枚举、调度模型、hook 事件、STATE 字段）。所有机制均已实现并验证（对应 SPEC 已 verified/pushed），本 SPEC 不改代码、只做文档化。

## Goals

- 26 项缺失机制全部获得可发现的文档描述，每项附代码锚点。
- 缺失配置键补进 09 章全键参考（键表行形态，含默认值/范围/生效方式）。
- STATE 字段清单与 `.fenix/` 文件地图补全到可支撑排障的粒度。
- 04/12/08 三处结构缺陷修复。

## Decisions

- **D1 与姊妹 SPEC 的文件级分工**：本 SPEC 在重叠文件（05/06/07/08/09/12）上的改动单元是「新增小节/新增表行/名称替换」，MUST NOT 删除或改写姊妹 SPEC 落地的新口径句子（如「缺省 5」「11 状态」「两段式 720/1080」）；实现时若姊妹 SPEC 已合并，以合并后文档为基线增量编辑；若姊妹 SPEC 尚未合并，本 SPEC 只增不碰其目标句子，merge 冲突由框架 wip gate/spec 目录在飞守卫兜底。
- **D2 新增内容的落位原则**：机制描述进其「用户遇到问题时会翻的那一章」（如 env 豁免握手进 05 验证体系、unseal 进 06 瞬断治理、取消保持态进 03 生命周期 + 08 Dashboard 操作、质量门禁进 08 + 05 交叉），而非集中新建一份「新机制汇总」——帮助中心的组织轴是使用场景不是提交历史。
- **D3 篇幅与锚点纪律**：每项机制一段到一小节（先「用户看到什么/该做什么」，再机制细节），禁止把 spec 设计文档整段搬运；每个数值（缺省值/秒数/上限）实现时 MUST 实读锚点核对，代码与本文记载不符时以代码为准。
- **D4 名称校准以代码字面为准**：分面 label、页签名、设置页页签数，实现时实读 `list.tsx`/`settings/index.tsx`/`detail.tsx` 的字面值再写入文档，不凭本 SPEC 文本转抄（前端可能继续演进）。
- **D5 fast-track 单次收口**：全部改动为 9 份 md 编辑，无代码验证依赖；验证采用 cli 形态关键词/结构断言（26 项特征词命中 + 三处结构修复核对），不启动浏览器。

## Risks

- **R1 与姊妹 SPEC 的并发窗口**：两个 SPEC 都改 05/06/08/09/12。缓解见 D1（只增不删）+ 框架层 wip gate；若实现时检测到姊妹 SPEC 已改写同一段落，以磁盘现状为基线，本 SPEC 的「新增」改为「增量补充」。
- **R2 篇幅膨胀**：26 项若每项展开成大节会让文档失焦。缓解：D3 篇幅纪律，长机制（code-fix 车道、质量门禁、会话分面）允许独立小节但以「用户视角两段式」（现象/操作 → 机制）为上限结构。
- **R3 文档锚点 id 漂移**：新增小节改变目录锚点。缓解：新增小节放在相关既有小节之后、不改既有标题文本，既有相对链接不受影响。
