fenixd 在 Windows 上以原生进程（非 WSL/模拟层）全功能运行的交付与验收面：PowerShell 安装链与服务环境注入、独立依赖清单、harness CLI 可执行解析与确定性 spawn 失败分类、dockur 过机验收通道与双平台 CI。平台机制差异（进程生命周期/情报/文件锁/托管接口/死法闭集/端口语义）单点收口在[平台抽象层（PAL）](../codebase-structure/platform-abstraction.md)，本页只装部署、安装与验收侧规则。

## 规则

- **部署形态**：claude code 与 dsh 以 Windows 原生进程运行时，fenixd 作为其增强 harness 必须同为原生进程，全功能对等（G1 清单口径，含边缘能力、不降级）；Windows 承载不得以性能降级的模拟层替代。
- **Linux 零变化硬约束**：Windows 支持的全部交付保持 Linux 行为逐位不变——Linux 全量测试零失败、静态守卫零豁免新增、`core/platform/linux.py` 除注记不改；Linux 侧安装（install.sh）与发布流水线（release.yml）不受影响。
- **harness CLI 可执行解析单源**：Windows 上 harness CLI（claude 等）的可执行解析单源化——**任何 spawn 点都必须消费同一解析 helper（`resolve_harness_executable`，`shutil.which` 透传）**，消费面覆盖 spawn-spec 构建、派发预检（`precheck_harness_executable`）与健康检查探针（dsh_adapter check_health 的 `--version`/`--dump-config` 双探针）；新增 spawn 点以 dispatch 主路径（spawn_argv0）为模板接入，不设豁免——裸名形态下「which 能找到的就是能 spawn 的」不成立；spawn argv[0] 用解析结果替换，裸名不得直达 `CreateProcess`——Windows 对无扩展名可执行文件只自动补 `.exe`，npm 安装的 CLI 仅有 `.cmd/.ps1` shim（包不带真身 exe），裸名 spawn 必败 `WinError 2`；argv[0] 替换仅 win32 生效——POSIX 裸名经 execvp/shebang 已可 spawn，全平台替换会引入 parent-env which 与 child-env PATH 查找的源漂移并使 SpawnSpec 快照金样本失配，违反 Linux 逐位不变硬约束；which 解析不到走 `HARNESS_CLI_UNAVAILABLE_MARKER` fail-fast 路径（健康门探针解析失败同标记、在发起 spawn 前先 fail-fast）。dsh 通道的 .cmd shim 包裹链路（dsh 工具侧实现）与本机制正交。
- **确定性 spawn 失败一跳终态**：spawn 阶段的 `FileNotFoundError`（errno 2/3，即 WinError 2/3 环境缺件）归类 infra-deterministic 终态——部署态环境缺件不会秒级自愈，重试无意义：不进重试队列、不重派、不触发同因熔断冻结与 arbiter 升级；预算净效果零消耗（退款经既有 `_exempt_infra_run_budget` infra 补偿通道，按 run_id 幂等）；终态 error MUST 带根因与修复指引（`[infra-deterministic]` 前缀标记单源，「<exe> 不在当前 PATH——按 install.md §8 服务 PATH 最小集补齐后 nssm restart」，dispatch 读侧按标记路由终态分支，fast-track 与常规实现车道双消费点）。run 失败归因三型分立：`spawn_failed`（spawn 缺件）/ `nonzero_exit`（非零退出）/ `result_missing`（结果文件缺失）；`result_missing` 归因附 run 转录 stderr 尾窗（截尾 2KB，防取证断链）。
- **优雅终止三层协议**：托管子进程（claude/dsh）终止顺序固定 stdin-close → `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT)` → 宽限等待 → `TerminateProcess`；树杀以 Job Object KILL_ON_JOB_CLOSE 为主、Toolhelp 快照枚举兜底；禁用 `taskkill /T`（leader 已退出时静默漏杀）。CTRL_BREAK 对 claude（干净退出码 0）与 dsh/node（退出码 `0xC000013A` STATUS_CONTROL_C_EXIT）均有效；`0xC000013A` 属控制台事件死法族，不得当普通非零退出码误标。
- **安装链 PowerShell 化**：`install.ps1` 幂等可重入，消费 `requirements-win32.txt` 装依赖；PATH 基线写 User 域（`[Environment]::SetEnvironmentVariable`）；软链需求走 symlink→junction→copy 三级降级链，无开发者模式特权时降级成功且降级方式留痕。
- **安装链可观测性（首装零噪音）**：正常首装路径（服务未安装 → 走安装决策）不产生 warning 级及以上日志信号——「未安装」是预期态，至多 debug 留痕；warning 仅用于拿到瞬时失败证据的场景（sc query 超时、退出码非 1060 的失败后纠偏路径等）。预期态判据是 `sc query` 退出码 == 1060（ERROR_SERVICE_DOES_NOT_EXIST）而非「非零返回」：sc 对未安装服务本身即以非零 1060 退出，按「非零 ⇒ 告警」的朴素口径实现，首装路径必然误报。`_sc_query`/`_service_state` 私有助手把失败证据（退出码/异常形态）透传给 `install_unit`（两者为 `_` 前缀私有助手，不属于公开进程 API 面）；`install_unit` 返回 JSON 形状（`ok/error/already/unit`）与服务安装语义不变。
- **win32 输出编码安全**：平台 logger 的 stderr handler 以 errors=replace 包装（handler 层形态，不污染进程全局 stderr）——GBK/cp1252 等受限控制台下含中文日志以替换符降级写出，不以 `UnicodeEncodeError` traceback 形态混入捕获流。`core/platform/win32.py` 全部 `capture_output` 的 `subprocess.run` 按 `text=True, encoding="utf-8", errors="replace"` 解码：sc/nssm 输出语义在 ASCII 域（SERVICE_RUNNING / STATE / 4 RUNNING），GBK 双字节只出现在中文服务描述等字段，替换降级不损判读且避免 cp936 平台 codec 依赖；GBK 输入不抛 `UnicodeDecodeError`、读线程不崩、不被归一成「状态查询无响应」假告警。该读侧口径是全库不变量而不止平台层：**跨进程读流禁止依赖 locale，凡 `text=True` 必显式 `encoding="utf-8"`**——CLI 产物恒为 UTF-8，受限 locale 下隐式按 locale 解码会把含中文的产物（patch 注释/插件描述等）解码崩溃、stdout 置空，下游按空产物误报假阴性（如 Bundle 挂载探测误报未挂载）；`errors="replace"` 保读侧健壮。
- **运行时日志卫生**：用户级配置「顶层不是对象，按空配置处理」为 DEBUG 级（注释-only 模板是设计内合法空配置，非错误）；`os.getpgid`（POSIX-only）平台守卫——win32 分支跳过取组/杀组链（`kill_process_group` 为全库唯一调用点，v2 dev-server 停止链等消费方随之覆盖）；dashboard 在 `handle_one_request` 层吞掉 `ConnectionResetError`/`ConnectionAbortedError`/`BrokenPipeError` 客户端断连类异常（debug 单行留痕，与 SSE 流路径既有同族捕获两层口径一致，不刷全栈 traceback）；框架源码含转义序列的 docstring 一律 raw string——Python 3.13 导入零 SyntaxWarning（宿主 3.10 编译期非法转义发 DeprecationWarning，复核用 `python3 -W error::DeprecationWarning -m compileall core bin`；≥3.12 解释器用 `-W error::SyntaxWarning`；只动字符串字面量不改语义）。
- **skill 部署文档双平台命令口径**：8 个 `skills/*/SKILL.md`（fenix-approve/archive/dashboard/new/process/prototype/setup/status）在首个可复制命令之前含统一「Windows 命令换算」注记——文内 `python3` 在 Windows 上一律写作 `py -3`，其余 Unix 形态命令按各节既有注记换算；高频命令行内双写限每 skill 最常复制执行的 1–3 处，禁止全文改写（保持 diff 可审）；注记不改变 skill 的触发条件、流程语义与任何代码。
- **制品与骨架完整性 fail-fast**：部署面完整性校验一律硬失败收口、禁止静默降级——`fenix-init` 在创建任何目录/文件之前前置校验骨架全读面（`.fenix/config.template.yaml`、`.fenix/config.user.template.yaml`、`FENIX_LINKS`、`AGENT_LINKS`、`templates/`），任一缺失 exit 2 + 逐项缺失明细，`render_config` 等后续失败时 best-effort 清理本次已建目录（不留半成品骨架）；`config.user.template.yaml` 是 install.ps1 侧硬读面，按制品完整性口径入清单校验，不得以「fenix-init 本体不读」为由移除。`fenix-init` 提供 `--version`（读包根 VERSION；缺失时输出 unknown 并退出 0——版本查询非部署关键路径，不 fail-fast）。骨架清单不引用源码根不存在的文件（`fenixd.py` 是唯一入口，包语义不需要 `__init__.py`，不在制品中虚构文件）。`install.ps1` 完整性自检在部署面/模板缺失时 exit 1 + 缺失清单，不以 WARN + exit 0 静默降级收场；与打包侧 `scripts/package.sh` 21 项断言构成双保险——打包侧防出包缺件，安装侧防解压/传输缺件。spec CLI 同口径：`fenix_spec.py new` 在写任何 `.spec.yaml` 前前置 `load_schema()` 校验 `schemas/spec-driven/schema.yaml` 可读，缺失 exit 非 0 + 修复指引（制品缺件按 install.md §3A 注记从 codeload tarball 补齐或升级制品版本），与 `status` 同一校验口径——不出现「new 成功而 status 崩」的半残脚手架。
- **Windows 依赖独立清单**：psutil / pywin32 必选；PyYAML / httpx / jsonschema 与 install.sh Linux 侧同源同版本下限；portalocker 保持注释备选态（C 组 msvcrt.locking 主选，弃用时才纳入）。Windows 依赖只进 `requirements-win32.txt`，不进 Linux 依赖面，不引入打包体系（无 pyproject.toml/setup.py）。
- **Windows 服务托管**：NSSM 为服务后端主选（备选 WinSW）；参数面以 NSSM 2.24 实测为准——无 `AppStdoutCreationBytesToPreserve`，`AppExit` 需双子参（`AppExit 0 Restart`），`nssm install <name> <exe>` 已钉死 Application、AppParameters 不得再带解释器（否则展开成 `python python script`，python 吃自身 MZ 头秒退并节流 SERVICE_PAUSED）。systemd 无直接对应的语义（SuccessExitStatus / TimeoutStopSec / EnvironmentFile 0600 / KillMode=mixed）逐条映射或显式文档化为 Windows 差异，不静默降级（接口面细则见 PAL 页 D 组）。
- **服务环境注入与自检**：`install_unit(root, env=…)` 支持以注册表 `REG_MULTI_SZ` 形态写 `Parameters\AppEnvironmentExtra`（元素 = "K=V" 列表，元素边界确定；不经 `nssm set` 多参数形态——引号歧义坑）；写入为 read-modify-write 合并语义——同键 K=V 覆盖、异键保留，install.md §8 手工 `Set-ItemProperty` 落的服务 PATH 最小集等既有条目不得被整值替换清除；写后须 `nssm restart` 生效（SCM 仅在进程启动时读环境块）。幂等重跑（already=True）与安装完成路径做服务环境自检——以服务 PATH 视角（AppEnvironmentExtra 内 PATH 条目，未配置回落系统 PATH）解析 claude/git/python（shutil.which 按 PATHEXT，与 spawn 侧同一解析口径），任一解析失败在返回 JSON 增 `env_defect` 明细（`ok` 仍 True——安装本身成功，缺陷是环境预警面），环境缺口在安装侧提前暴露而非派发烧轮后才可见。
- **服务化 USERPROFILE 缺省注入**：`install_unit` 未显式传 `env` 时缺省并入安装调用者 `USERPROFILE`——安装时刻 `os.environ["USERPROFILE"]` 与 `Path.home()` 双读锚定取非 systemprofile 侧（env 侧优先；两读皆 systemprofile 或皆空则跳过注入并在返回 JSON 附 `userprofile_skip` 人读提示，不 fail 安装——安装调用者可能已在服务上下文运行，须由交互式管理员会话执行安装）。缺省注入仅限 LocalSystem 承载形态：新装 NSSM 服务默认 LocalSystem 恒注入；已装服务经服务账户判定（`sc qc` 的 ObjectName，同源免 locale）为非 LocalSystem 专用账户时跳过——该形态 SCM 已为账户提供真实 profile，注入安装者 profile 反成覆写错误值。显式 `env` 同名键以显式值优先。LocalSystem 服务进程因此解析真实用户 profile 而非 `C:\WINDOWS\system32\config\systemprofile`，`%USERPROFILE%\.fenix\config.yaml` 不再因服务环境漂移误报不存在；G1-01b 过机复验（缺省注入 → 幂等合并保留手工条目 → nssm restart 后服务内 `Path.home()` 解析正确）PASS。
- **服务化用户级配置漂移判读与存量补救**：服务化部署出现设置页「用户级配置文件不存在，表单为默认值」、`/api/config` 返回 `raw_exists=False, scope=user`，而 `%USERPROFILE%\.fenix\config.yaml` 实际存在时，判定为服务环境 USERPROFILE 漂移误报（LocalSystem 服务未注入 USERPROFILE 时 SCM 环境块指向 systemprofile；`USER_CONFIG_DIR` 在 import 期按进程 home 一次性绑定，事后改注册表不 restart 不生效），不按「文件被删」处置。存量服务补救配方：管理员 PowerShell 对 dashboard 与 supervisor 两服务的 `HKLM:\SYSTEM\CurrentControlSet\Services\<svc>\Parameters` 写 `AppEnvironmentExtra`（MultiString，supervisor 侧先读后追加、不清既有条目）注入 `USERPROFILE=C:\Users\<user>`，`nssm restart` 两服务后以 `(Invoke-RestMethod http://127.0.0.1:8787/api/config).raw_exists` 转 True 复验（install.md §8 附存量补救一键命令）；漂移面亦可注入 `FENIX_HOME` 逃生口（用户级配置目录按其解析，见[分级配置页](../provider-models/hierarchical-config.md)）。
- **安装手册一步形态口径**：install.md §8 服务环境注入以 `install_unit(root, env=…)` 一步形态为新装服务主路径（env= 携带服务 PATH 最小集 + DSH_HOME + LLM_API_KEY；USERPROFILE 无需手工携带——缺省注入已覆盖），页内手工注册表 `Set-ItemProperty` 块仅用于已装服务的补配/审计；「先装服务、后手工补注册表再 restart」的两步形态留出裸 PATH 首启窗口（服务以裸系统 PATH 首启，env_defect 检出而注入半边无过），新装一律一步注入，不得回退两步教程形态。USERPROFILE 注入为 §8 必做项：一步形态缺省即注入调用者 profile，存量补救与手工 nssm 路径同节给出，§4a 附服务化保障注记、故障排查章附漂移判读条目。
- **过机验收通道**：验收口径为 `tests/integration/windows/` 三件套（README 通道拓扑 / run_integration.ps1 一键驱动 / g1_full_parity_checklist.md，G1 全功能对等 25 条），承载于 dockurr/windows 容器内的真实 Windows Guest（宿主 8006 web 观景台）。通道执行走 win-vm skill 标准姿势：win-test 容器 + SSH `127.0.0.1:22222` 直连（密钥 `~/.ssh/winvm_admin`，`wr.sh` 需 `export HOME=/root`）；Guest 内访问宿主代码统一 UNC `\\host.lan\Data\...`。dockur 自带 RDP 凭据由 `docker run -e USERNAME/PASSWORD` 一次性注入、事后不可读取，通道选型不得依赖事后读取 RDP 凭据；`Z:` 盘映射是 per-logon-session 的（net use 不持久），不作通道依赖。Guest 内 Python 由容器 `/oem` 的 install.bat 装——OEM 钩子仅新盘首次装机期生效，存量盘不重跑。
- **过机通道实测纪律**：
  - 原生 exe 输出编码不可正则判：NSSM 原生输出 UTF-16LE，PS 管道捕获即乱码；服务/进程判态走 SCM API（`Get-Service`）等价替代。
  - 含非 ASCII 的 ps1 必须 UTF-8 BOM（PS5.1 否则按 GBK 解析吞引号报 ParserError）；宿主端编辑工具会剥 BOM——每次编辑后补 BOM 并以 xxd 验证，双 BOM 会被 PS 当乱码秒死。
  - SMB 陈旧窗口：宿主 mv 换新 inode 后 Guest SMB 客户端秒级缓存旧内容——宿主改 ps1 后等 ≥15s 或先由 Guest 探针核对再起跑；Guest 内 log rm + 立即 UNC 重定向存在 "The parameter is incorrect." 竞态。
  - Windows OpenSSH 每会话一个 Job Object：SSH 命令返回即整树回收 Start-Process 子进程；长活进程用 WMI 代生（`Invoke-CimMethod Win32_Process Create`）。
  - SSH/非控制台会话的中文输出统一 `PYTHONIOENCODING` / `reconfigure(errors="replace")`（cp1252/GBK 控制台会因 UnicodeEncodeError 崩掉整链）。
- **环境止损纪律**：「环境依赖」类归因必须先排除通道选型错配（凭据误依赖、姿势偏离 win-vm 标准姿势；如 G1-16~23 命令面实为纯本地、凭据归因不成立），按标准姿势重建通道复验后方可判定环境真缺；通道真不可用连续 ≥3 次失败即冻结过机验收并转 partial 登记，禁止宿主侧反复重试突破止损线；SKIP 逐项附环境阻塞证据；通道恢复后由 G1 清单一次性补验。
- **双平台 CI**：`windows-integration` workflow 以自建 runner 三标 `[self-hosted, Windows, dockur]` 过机，timeout 90 分钟有界；runner 离线时任务排队而非标红（concurrency 取消同分支堆积，防恢复后连环重放）；合入判据双绿——Linux 全量测试与 Windows G1 清单任一失败阻断合入。
- **过机复验铁则**：Linux 侧全绿是过机暴露缺陷的常态而非反证（G1 复验暴露的产品缺陷全部仅此通道可见，如 /proc 只读、cp1252 print、DWORD 有符号/无符号、NSSM 参数表、stdout 编码、UNC 长路径）——任何「Linux 全绿所以没问题」的结论必须过机复验后才可信；win32 后端与部署/承载脚本改动以 G1 清单过机复验收口，G1-24/25 回归钉住 Popen 句柄附加、ctypes 句柄原型声明两类回潮面。

## 关键行为

- `run_integration.ps1` 执行序列：Python/依赖自检（提示缺失时先跑框架根 install.ps1）→ 平台面 pytest 子集（`tests/test_platform_pal.py` 全量 + `tests/test_platform_guard.py`，Windows-only 用例过机不再 skip）→ G1 清单逐项执行并汇总 PASS/FAIL，任一 FAIL 退出码非零。
- win32 契约测试两层形制：Linux 可跑层（import 卫生/纯逻辑闭集）持续守护，Windows-only 层 skipif 门 Linux 跳过、过机生效（细则见 PAL 页关键行为）。

## 代码锚点

- 安装链：`install.ps1`、`requirements-win32.txt`
