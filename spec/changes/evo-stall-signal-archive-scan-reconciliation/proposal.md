# 提案：停滞信号扫描面归档盲区对账

## 背景与问题

车道 API 停滞日预算信号（lane_stall_daily_budget）与单轮停滞升级信号（api_round_stall_escalated）共用同一 run 档案扫描循环，扫描面为 runs 目录顶层 glob（core/admin_monitor.py:4459-4461），不含 archive/。而 runs 保留清理约每 5 分钟一拍，终态 run 在落盘后 0-5 分钟内即被移入 archive/、永久退出扫描面；巡检节拍同为 5 分钟。

该竞态已从假说升级为实证：历史 4 组落账均为擦边赶上（落账仅比归档早 148s/27s/4s，最险 4 秒）；2026-11-25 窗两次窗口内无巡检轮即漏——code-review-1795622572 车道日累计 2819.1 秒（超 30 分钟预算线 57%）首次零告警，code-fix-1795638803 单轮停滞 370.9 秒（终态 error 无豁免资格）使 api_round_stall_escalated 面保持自上线零落账。已合入的 7a6362592 修复（stat 瞬时失败永久零入账窄缺陷）不改扫描面，无法覆盖此盲区。

## 目标

1. 两个停滞信号面的扫描面覆盖 archive/：终态 run 已归档的档案仍可入账，消除「终态落盘→归档窗口窄于巡检节拍」的漏报。
2. 对账自证：每巡检轮将终态 run_metrics 停滞行合计（含 archive 内当日终态 run）与内存累计器对账，差额超阈值补发 lane_stall_daily_budget 信号留痕——不依赖根因裁定的确定性兜底。
3. 知识页 api-stall-observability 补记该竞态盲区与对账机制。

## 非目标

1. 不改停滞阈值（60s 记账线/300s 升级线/30 分钟预算线）与信号语义。
2. 不处理 5 条历史积压告警的清账（人工作业，走 dashboard/台账既有通道）。
3. 不改 runs 保留清理的归档节拍（其本身按设计工作）。

## 方案概要

扫描面从顶层 glob 扩展为「顶层 + archive/」（或归档事件时点触发补充入账，二选一由设计定）；对账自证以终态 run_metrics 行合计为基准、差额超阈值补发信号，入账去重沿用既有 run 级去重集合防重复。两者并用：扫描面扩展治归档盲区本因，对账自证兜底其余漏计形态。

## 与既有交付的关系

存量锚点为在途 SPEC evo-add-lane-stall-daily-budget-accounting（已 pushed）：其交付面（记账、阈值、信号、重启重建）不含对账自证/累计器落盘/扫描面扩展（grep 其 tasks 与 design 证实），design 3.2「重启重建」依赖顶层在盘文件、archive 场景不在覆盖面。本立项为该交付的可靠性补强，机制正交不重复。
