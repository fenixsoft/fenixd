## 背景

自 2026-09-29 夜起连续 7 夜，code-fix 夜间批链每夜恰有批次在本地 04:19-04:30 启动、于 04:30 上游断窗中死亡（api_timeout 终局，ENOTFOUND）。系统日志证实该断窗为每日固定时刻事件：/var/log/syslog 连续 9 天本地 04:30:01-04:30:02 enp42s0 与 wlo1（两块物理独立网卡）同秒 Lost carrier，04:30:59 恢复、04:31:2x 再断、04:31:23 恢复；本机无任何同时刻定时任务触碰链路，根因在共同上游侧。

## 问题

既有防线（连接类失败 300 秒短冷却、api_timeout salvage、跨日指纹观测）均为事后缓解：每晚仍烧掉一个在跑 run（约 14 分钟、百余轮 API 往返、$5+ 真实成本），下一批再经冷却推迟约 28 分钟才恢复。窗口时刻逐秒确定，而批链投递对窗口无感知，属可避免的确定性损失。

## 目标

给 code-fix 批投递加「每日静默窗」：本地固定时刻区间内投递入口拒绝启动新批，窗末自动放行，使批次不会被启动进已知断窗；损失从「死一个 run + 推迟半小时」降为「链路暂停约 25-30 分钟」。

## 非目标

- 不改 api_timeout 终局判定与 salvage 逻辑（窗口外的连接类瞬态仍按现状处理）。
- 不解决在跑长批横跨窗口的死亡（观测上批次均为短批，静默窗已覆盖实际形态；长批横窗属残余风险，由 salvage 兜底）。
- 不修上游网络本身，不引入对上游可用性的主动探测。
