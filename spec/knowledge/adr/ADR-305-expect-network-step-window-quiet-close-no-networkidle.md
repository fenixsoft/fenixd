# ADR-305：expect_network 挂交互步骤窗口，固定静默窗收窗并禁用 networkidle

date: 2026-10-30
status: accepted

## Context

机械 web 场景对「交互触发重拉取」类缺陷结构性失明：既有断言器面向页面态与 API 响应体，无「步骤执行窗口内网络行为」维度，此类缺陷只能靠昂贵的 LLM 验证轮偶然发现且无法回归锁定（command-center 筛选切换 0 新请求滞留 60s 实证）。补网络断言必须先裁定窗口归因——请求落入哪个步骤的窗口要无歧义；同时本仓库页面常驻 SSE 推流，以 networkidle 判定「网络安静」永不满足，任何以「网络空闲」为前提的等待机制在本仓库不可用（browser.py 模块头既有设计决策已移除该等待）。

## Decision

- `expect_network` 挂在交互步骤上与操作同对象，监听窗口 = 该步骤执行起止；不做独立 `expect_network` 步骤 op，不做全场景级网络快照（独立 op 存在上一操作的请求落入本步窗口的归因歧义，全场景快照有跨步骤归因歧义）。
- 窗口收尾用固定短静默窗（单轮 300ms 连续无新请求即收窗，总时长封顶 1500ms），MUST NOT 使用 `wait_for_load_state("networkidle")`；后续 browser 自动化演进引入任何等待机制，同样禁以 networkidle 为判据。
- 漏计只允许保守方向：窗口截断只会让「该过的场景失败」，结构上不允许产生假通过；字段坏档（绕过验收的残档）按断言失败收场，不给「坏档 = 无断言 = 通过」留通道。
- URL 模式匹配（纯子串 / `re:` 前缀正则）与字段形态定义单点收口，验收校验与引擎断言共用同一口径，防两处各自漂移。

## Consequences

- 尾部延迟请求（操作完成后数百毫秒才入栈）被静默窗兜进窗口，不漏计；常驻 SSE/高频轮询页面单步骤最多空等封顶时长（1.5s），场景集大时验证耗时随之线性增加。
- 背景轮询请求可能与断言窗口重叠造成误计，引擎不做背景请求过滤（保持机制简单），由场景作者以精确端点子串区分；场景易碎风险由契约示例的稳健形态（端点子串 + min_count: 1）与 min_count > 3 WARNING 引导兜底。
- 交互/非交互显式集合与单点形态定义约束后续场景 schema 演进：新增窗口级断言字段须沿用「挂步骤、窗口 = 步骤起止、验收/引擎单点同源」同构模式，另起独立 op 或第二套形态定义须显式 supersede 本 ADR。
