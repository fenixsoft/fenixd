# ADR-291：进程清场击杀统一守卫收口，禁命中调用者自身进程组且禁单 pid 降级回退

date: 2026-10-28
status: accepted

## Context

测试替身 proc 的 pid 怪值（0、-1 等）流入产品清场代码时，`os.getpgid(pid)` 解析到调用者自身所在进程组，或 `os.killpg(0)` 直传经 `kill(-pgid)` 折算等价自身组广播，清场动作反噬宿主——2026-10-07 两起同构事故中，全量回归套件被 pytest 主进程自身所在进程组击杀（-9 与 -15 两个信号变体，ftrace 取证发送者即 pytest 自身）。逐个修替身是打地鼠：任何存量替身怪值或未来新增的替身、清场点都可能复发，且直传型清场点语境下 `-1` 折算为 `kill(1)` 属误投递，数值层面不可判别。

## Decision

core 全部清场击杀路径统一收口到 `core/proc_utils.py` 单一守卫助手 `guard_killpg`：信号发出前校验目标 pgid 不等于调用者自身所在进程组（`os.getpgid(0)`）且 pgid 为正值（非正值单独拒绝，数值比对自身组挡不住 `killpg(0)` 的折算广播）；命中即拒发、记 WARNING（含调用点标识与目标 pgid）、按「组已不存在」语义静默返回。调用方对拒绝一律按组不存在静默收尾，不得回退触发单 pid `os.kill` 降级（`os.kill(0)` 同样是自身组广播）。清场点仅替换信号发出的最后一跳，SIGTERM → 宽限 → SIGKILL 序列语义逐位不变。grep 断言测试钉死 core 下裸 `os.killpg` 清场调用零存在（探活调用点显式豁免）。守卫永远开启，无配置开关。后续任何新增清场点必须经守卫，禁止绕过。

## Consequences

- 业务上不存在「合法清理调用者自身组」的场景，守卫误拦面为零；真孤儿组清理不受影响（孤儿组 pgid ≠ 调用者自身组）。
- 测试替身 pid 怪值的「不可达」表达被规范为正值越界 pid（超出 Linux 默认 pid_max），禁用 0 与 -1；替身修复与守卫互为冗余防御。
- 守卫只覆盖 `os.killpg` 清场语义：`os.kill` 单 pid 击杀与未来新形态的清场原语不自动受保护，须显式纳入守卫面或以同类守卫扩展，否则留下同构自伤通道。
