# ADR-298：全仓快照核销解锁单点收尾覆盖守卫、待核销锚仅观测通道

date: 2026-10-30
status: accepted

## Context

全仓快照核销把「本轮未再观测到的 open 条目」置 resolved，判错即白洗——未审文件的存量问题被静默抹掉，且不可逆（resolved 台账条目不再进默认视图）。核销资格从「仅 manual_full」放宽给 scheduled 全仓档（window_start=None）后，核销发生点从单一手动全仓扩展到周期收尾与重派链；同时 error 收场抢救落账留下「部分覆盖」现场，需要跨 run 记账与联动清除。若解锁判定散布到消费侧（调度器读锚自行解锁、新派发通道自带覆盖口径），部分覆盖白洗面会随消费方数量线性放大——已实测的形态是：以「剩余清单」为覆盖基准的派发通道若绕开守卫，会把部分覆盖恒判为解锁。

## Decision

核销解锁判定唯一实现点收口在 run 收尾的覆盖完整性守卫（agent_runner/maintenance_runs 收尾段：「累计覆盖 ⊇ 完整 manifest」+ observed 非空门），重派链分支与普通全仓分支同语义；调度消费侧（admin_monitor）不重复实现解锁判定。pending-writeoff 锚（`.fenix/code-review/writeoff-pending.json`）只承载「存在部分覆盖待核销」的观测事实——供完成日志标注与核销后清除联动，绝不参与解锁门控。后续任何要在核销链路上派发的通道（如锚驱动的剃余续审）必须复用既有 `redispatch_of` 形参进入守卫消费段，按原 run 及其链产物累计覆盖判解锁；另起新形参会落入普通全仓分支、以剩余清单为覆盖基准恒判解锁，属禁止形态。剃余派发只优化「少烧钱」，不改变解锁权威。

## Consequences

锚读取失败/缺失只丢完成日志标注，不影响核销正确性（观测通道 fail-open，与解锁门解耦）；覆盖不完整时锚滞留在位、完成日志持续标注待核销态，等补齐轮收尾守卫清除——锚的生命周期与收尾对账绑定，不存在「锚在但解锁」的中间态。代价：① 解锁判定的可见性收在收尾段一处，调度侧排查核销问题必须读收尾守卫逻辑，不能以锚状态近似；② 新派发通道接入核销链路的形态被钉死为 redispatch_of 复用，想绕开须显式 supersede 本裁定；③ 部分覆盖期间每轮周期审查都走剃余路径（读锚 + 累计覆盖计算），引入少量固定 IO 成本，换取不整轮全量重烧。
