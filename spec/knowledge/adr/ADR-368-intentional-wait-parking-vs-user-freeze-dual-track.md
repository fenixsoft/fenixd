# ADR-368：框架有意等待态与用户冻结语义分轨——停泊复用 _frozen_hold 但 frozen 恒不置位

date: 2026-11-16
status: accepted

## Context

judge 拒收转纯归因后，spec 停在无驱动的可调度 testing 态会被孤儿探测告警、被恢复路径无条件重派全量验证，重放同一未修复缺陷直至 rerun 计数触顶冻结——结构性不可收敛回环。需要一个「框架有意等待」的保持态，但状态机已有完整的用户冻结语义族（派发由 frozen 挡、blocked_stuck 豁免、unfreeze 流程、dashboard 冻结标签、冻结清理豁免、冻结终止现场保全续做）。若停泊整套复用 frozen 语义，框架等待态会被误当用户冻结处理：冻结标签误亮、续做路径误触发保留分支恢复。

## Decision

框架有意等待态（纯归因停泊）与用户冻结语义永久分轨：停泊复用 `_frozen_hold` 字段置位并留痕原因（零新增 schema），但 `frozen` 字段不得置位——冻结连带语义全部为用户冻结专用。停泊的不可调度性不靠该字段自身（其单独置位不挡任何链路），由无驱动共享判定 `spec_is_undriven` 单点的停泊检查达成（孤儿探测与恢复路径同源消费，禁调用点各写一份），停泊判定收口 `spec_is_parked` 单点（_frozen_hold 置位且 frozen 不在场）。退出锚点收敛三处：人工处置（unfreeze）、新修复 run 落地、场景集变更；停泊态经 unfreeze 退出按普通解冻清理 + 重派，不触发冻结终止现场保全的保留分支续做。

## Consequences

后续一切「框架有意等待」类机制须沿此分轨：复用 _frozen_hold 须过 spec_is_parked 语义判别，不得置 frozen 借用冻结连带语义，也不得在探测/恢复调用点另写停泊判断。代价：_frozen_hold 一个字段承载两种语义（冻结终止现场保全 / 纯归因停泊），判别完全依赖 frozen 是否在场——续做解析与停泊判定两处消费点都必须维持该前置检查；停泊可见性不新增 UI，人工核查走停泊原因留痕字段。
