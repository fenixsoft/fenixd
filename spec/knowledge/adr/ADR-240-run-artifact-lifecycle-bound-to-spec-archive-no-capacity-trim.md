# ADR-240：run 产物生命周期单轨绑定 SPEC 归档，禁按容量上限裁剪生产数据

date: 2026-10-06
status: accepted

## Context

run 产物的容量治理两度以「保留 N 条最旧优先删除」形态出现、两度造成生产数据损失：2026-09-09 remove-auto-run-cleanup 曾废除按数量裁剪并删除 runs.keep 配置；2026-09-21 fix-dashboard-read-path-performance 又将 runs.keep 落地为归档目录的真实消费点。归档上限压的是文件数而非 SPEC 数——本项目吞吐 67~75 文件/天，50 槽位每天翻转 1.5 次，归档产物存活期不足 24 小时；2026-09-27~28 未归档活跃 SPEC（add-knowledge-atlas）的全部 21 个 run 产物被物理删除，SPEC 时间轴运行节点全灭。反向缺口是 `runs/archive/` 中 36% 条目属无主车道产物（code-fix / admin-global / code-review），若清理单纯挂靠 SPEC 归档将无限堆积（≈9000 文件/年）。ADR-059 确立的「顶层只增不减、离开顶层唯一入口=SPEC 归档、容量治理须带审计重新立项」在本 SPEC 处兑现：这次立项就是那次带审计的重新立项。

## Decision

1. 产物生命周期单轨绑定 SPEC 生命周期：SPEC 未归档产物可回看，SPEC 归档产物即清理；清理挂在 `archive_spec_runs` 唯一入口（从顶层与归档副本两处一并删除），不新增第三入口，后续一切归档路径必须收敛到它。
2. 归档目录禁设容量上限：归属活跃 SPEC 的产物在其 SPEC 归档前不被任何路径删除；活跃目录有界性由「终态即移出」保证，归档目录有界性由「SPEC 归档清理 + 无主产物 14 天天龄兜底」双机制保证，不以 keep 类配置项承载。
3. 无主判定（`run_spec_part` ∉ `spec/changes/` 活跃目录名集合）每次清扫现算不缓存，使 SPEC 归档后未删净的残留自动落入无主集形成双保险；活跃 SPEC 集扫描失败时跳过本轮兜底清理（fail-closed，宁堆积勿误删）。
4. 一切产物删除逐文件审计日志 + 单周期批次上限，禁静默大批量删除；`runs.keep` 配置面（读侧消费、config_admin 受管键/回显/写入分支、同文件兜底校验）整体拆除，存量 YAML 残留为无害死键零迁移。
5. 后续 SPEC 不得以性能、磁盘、简化为由重新引入按数量/时间裁剪活跃 SPEC 产物的机制；保留期如需可调，按「配置项必须带 Dashboard 界面」约定另行立项。

## Consequences

SPEC 归档后 LLM 对话转录不可回看、时间轴运行节点消失（状态节点来自 daemon 日志不受影响）；终态 SPEC 耗时/成本汇总已固化进 STATE.md 不受损。未归档 SPEC 多且 run 量大时归档目录增长快于有上限时期（约 15MB/天量级），由双兜底机制约束在 SPEC 生命周期内收敛。治理代码须长期维护无主判定的 fail-closed 防御——活跃集误判为空集即大规模误删，这是本裁定最尖锐的失效模式。
