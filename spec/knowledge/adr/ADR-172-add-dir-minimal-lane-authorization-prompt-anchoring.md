# ADR-172：授权目录注入是工作区边界信号——按车道最小授权，提示词落点逐车道锚定

date: 2026-09-28
status: accepted

## Context

runner 曾无条件为每个 run 注入主树 verify-progress 的 `--add-dir`，而提示词「唯一例外：验证进度目录（框架已显式授权）」一词同时指两棵树。实现者据「授权 = 可以写这里」选择主树绝对路径落盘，产物门却读 worktree 内路径——写读错层导致 7 次重试全失败（同 ADR-171 事故）。根因是注入与措辞共同把「verify-progress 是主树共享目录」这一对部分车道成立的事实外溢到了产物落点在 worktree 的车道。

## Decision

- `--add-dir` 的语义是「这个目录是你工作区的一部分」的显式信号，必须按车道最小授权：只有产物真实落在共享树的车道注入；产物落点在 worktree 的车道（implementer/repair/spec-review）不注入——对它注入本身就在制造写错层的机会。
- 未知 agent_type 缺省保持注入：既有调用点（维护/admin/dashboard 会话）语义不变，精化只对显式列举的车道生效。
- 提示词对产物落点的表述必须与门读取层同源、逐车道锚定：worktree 落点车道写明「相对当前工作目录（worktree）的相对路径」并明示「写主树同名目录会被产物硬门判缺失」；同一提示词段内禁止残留「被显式引用、却已不在授权目录内」的共享树绝对路径字样，落盘指示与「仅供框架读取」声明二者取一并同轮收敛。
- 「授权目录」措辞禁一词多树：同一术语对不同车道指不同树时必须逐车道说明是哪一棵。
- 拦截 hook 为 gitignored 自举物、无法作为仓库交付物时，修复取「消除诱导 + 读侧兜底」组合，不依赖拦截面。

## Consequences

- 注入精化后若某车道依赖未列举的共享树目录会静默失效——各车道写入面须有明确清单并逐车道测试断言。
- 残余「绝对路径写共享树」通道由读侧多候选回退（ADR-171）兜底；诱导消除与误判兜底是同一契约的写读两半，新增 agent 车道时须同步核对注入表与落点表述。
