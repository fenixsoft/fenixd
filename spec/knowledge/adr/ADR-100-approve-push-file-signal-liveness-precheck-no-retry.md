# ADR-100：审批推送跨进程走文件信号单轨，写前探活

date: 2026-09-17
status: accepted

## Context

推送核心逻辑（单飞锁、main 先行 SHA 去重、指数退避、归档收口）全部收敛在 daemon 进程内；dashboard 是独立进程不持有引擎实例。跨进程直接推送是双轨实现——绕过单飞锁重引双 push / 重复 project log / 终态重复转换竞态，绕过退避计数与 daemon 侧重试互相干扰；历史上状态双轨并行产生过「解冻后半死态」事故。

## Decision

- 有状态写操作禁 dashboard 进程内双轨直接执行：跨进程执行一律走文件信号（原子写落盘 → daemon 主循环轮询拾取 → 读取 → 删除 → 执行），复用 daemon 侧既有写入口全语义（锁 / 退避 / 幂等 / 归档收口）。
- 信号写入前探测 daemon 存活，未运行前置 409 拒绝——信号无人消费时静默滞留比明确报错更糟；审批推送的触发时机（SPEC 刚 done，用户回来看）恰是 daemon 可能未启动的高发场景，探测为只读 /proc 检查成本可忽略。
- 消费失败不重试：各失败源各有既有兜底——幂等拒绝（重试无意义）、退避期内（恢复扫描重放）、推送失败（已写退避标记或升级信号）；消费侧重试反而绕过退避节奏，WARNING 留痕结束。
- 信号 payload 极简：无可注入参数的字段一个不加（全部行为由配置与 STATE 驱动），防与 daemon 侧实现漂移；source 字段留溯源。
- 已滞留信号无害：daemon 下次启动照常消费（执行幂等），不阻塞调度。

## Consequences

- 审批推送闭环不离开浏览器且零双轨语义，CLI 入口共存（入口增强非替代）。
- 同步执行阻塞主循环的代价先接受（push 超时上限内）；实测不可接受再移 worker 池，与既有重操作同模式。
- 升级窗口「新 dashboard + 旧 daemon」组合信号滞留无害，升级完成后自动消费；消费前 spec 被人工迁移到非 done 则幂等拒绝，信号已删无重试风暴。
