# 提案：维护型工作轻量登记台账（maintenance-work-ledger）

## 背景

框架流水线只有 spec 全流程一种记账形态：spec done 后的延伸/维护型工作与散件没有认领出口。实证（2026-10-08 复核）：potplayer-base 的延伸提交 6f1042e（82 文件，含 19326 行中性化补丁）无任何 run 认领、STATE 未动；散件 .fenix/bin/analyze_run_latency.py 未跟踪且无归因。后果是散件从产生即无主：告警无法路由认领、记账不可见、证据滞留。

核查同时修正了原始条目的证据基线：框架代码的常规修改多数已由有名 run（code-fix/impl/evo）认领落树，真正的缺口仅是「spec done 后延伸工作与散件」这一类不适合走实现→验证流水线的工作。

## 目标

1. 提供最小登记通道：一行登记（时间、范围、执行者、证据位置）落到项目级台账文件，延伸/维护型工作开工或收尾时可自助落账。
2. run 体系可识别登记型工作：新增 maintenance- run id 前缀与类型映射，使登记型 run 在告警归因与盘点视图中不再落泛型「无主 agent」。
3. 台账条目可与 run id 关联，供告警路由与复盘引用。

## 非目标

- 不扩展 STATE.md 准入语义（_admit_entry 现丢弃非 spec 记录，改动会引发全条目重写风险）——台账用独立文件承载。
- 不做执行流水线：台账定位是「已登记但轻量」的记账载体，不派生实现/验证车道。
- 不把「stale_code 自愈重启频率回落」列为验收指标：重启源头多为合法 run 落树经跨项目硬链接耦合传导（两仓库 .fenix core 文件同 inode），与本通道无因果；该耦合问题另行处置。
- 不处理存量散件的追溯登记（由散件处置类 spec 与人工认领收口）。

## 验收口径

- 台账追加/读取/容错有测试；坏行不中断。
- maintenance- 前缀在 RUN_ID_AGENT_PREFIXES 与 admin_monitor 消费表中均可识别。
- 登记条目可携带 run id 关联。
