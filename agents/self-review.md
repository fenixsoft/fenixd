## 你的任务
基于上述近 24 小时数据，识别该时段工作中的 **浪费 / 失误 / 可改进** 三类条目。

### 条目质量标准（每条 MUST 同时满足）
- **含影响**：量化后果——runner 时长 / run 轮数 / token 或金额 / 不可用时长 / 波及范围；无已发生损失的改进类条目写「复发敞口」（同类事件再次发生的单次代价，引用上次实测数字）。**MUST** 用第一句先说清「发生了什么 + 多严重」，再补数字；**MUST NOT** 让时间戳或裸 ID 占据第一句。
- **含证据**：具体数字、事件、run_id、告警 id、时间点——可回溯核实，禁止泛泛而谈。每个裸 ID / 告警 id / 字段名 **MUST** 带一句「这是什么」的前缀（如「告警 8742ae7357f9（stash pop 冲突信号）」），**MUST NOT** 只甩一串 ID。
- **含调查评估**：每条产出前先完成只读核查，写入 `analysis` 字段（调查过程与评估），让读者**零追问**即可判定「是什么问题、值不值得立项」：
  1. **核实**：evidence 引用的 commit 用 `git log`/`git show` 核实内容与时间，事件链与数据摘要/admin 记录交叉核对；核实不了的写明「未核实」，禁止编造或臆测。
  2. **评估**：根因归属（一次性失误 vs 系统性缺口）；与既有修复/在飞 SPEC 的关系——查 `spec/changes/` 活跃区与 `spec/archive/` 归档后写明是互补、重复还是已覆盖（引用 spec 名）；残余缺口与代价。
  3. **归因证据边界**：结论层级必须与证据覆盖层级一致——凡结论涉及根因归因，MUST 逐项对照当日可回收证据（失败明细档/告警/日志/commit）；证据只覆盖失败形态（如明细 items 为空、fallback_full=true、total=0）而不足以在多个根因假说间裁决时，结论只写到形态层、根因写「未定、多假说并存」并列出假说，**MUST NOT** 给出单因确定性叙事，**MUST NOT** 据此建议针对特定根因的修复方向（如按「模型改坏代码」假说建议预检重跑）——此形态下建议动作仍须给出（满足「含建议动作」标准），但转向取证/止损方向（如补齐失败面明细留存、加预检），不依赖未证实的根因假说；证据足以裁决单一根因时（如根治提交自述、可复现的最小证伪）才可给确定性归因，并附证据引用（commit/日志行/明细档字段值）。发现既有条目归因有误时以新条目显式更正（写明证据与正确结论），不回改历史条目原文（todo.md 历史由 git 提交固定，回改破坏审计链）。
  4. 组织顺序：先给「在处置哪个 spec 时暴露」（问题源），再按 已核实事实 → 根因 → 与存量工作关系 → 结论，3-6 句。调查仅限只读操作（git log/show、读源码与 spec/、.fenix/ 记录），禁止任何写操作。
- **含建议动作**：明确、可执行的动作。
- **术语即写即释**：框架术语 / 告警 kind / 字段名 / spec 名在条目中首次出现时 **MUST** 用括号或同位语给出白话解释（如「orphaned_state（无活动 run 的孤儿态探测）」），**MUST NOT** 默认读者已知。
- **可起草性**：改进类条目清晰度须达到「未参与该时段工作的新 agent 可据此直接起草 SPEC 提案」（如「CLI 秒挂 61 连发」→ 证据：次数/时长/根因；建议：连续 ≥3 次秒挂进入冷却）。
- **含短标题**：每条先给 `title` 字段——一句话短标题（≤30 字，概括「对象 + 发生了什么 + 后果」，不带句号），框架渲染为条目标题行；读者扫标题即可定位事件、决定是否展开读明细。**MUST NOT** 用 `a/b` 斜杠缩写堆叠（如 `Exit 143/-9`、`5/7`）代替完整描述。
- impact/evidence/suggestion 三个字段各写一两句裸内容（不带「影响：/证据：/建议：」前缀，框架渲染时自动加）；调查细节全部放 analysis 字段，不挤占这三个字段。

### 分类定义
- **浪费（waste）**：无产出价值的消耗（token/时间/重复劳动），如秒挂风暴、重复 run、空转等待、plan 丢弃。
- **失误（mistakes）**：执行层面的错误（配置失误、状态误置、合并/提交遗漏、超时），需指出根因。
- **可改进（improvements）**：系统性改进点，足以支撑后续 SPEC 立项。

### 中途信号（数据摘要第六节）的用法
数据摘要第 6 节「中途信号（含成功 run）」是含成功 run 在内的**过程性证据来源**，覆盖终态分类看不到的中途浪费与险情：
- **初筛离群 run**：run 指标（turns / cost_usd / duration_seconds）超过同 agent_type 组中位 ×3 的 run，**终态成功者也入选**——成功收尾不等于过程无浪费。
- **事件流深扫**：离群 run 的 API 停滞（stall 计数、最长往返 max_gap）与中途 error/stderr 事件痕迹。
- **编排救回痕迹**：fenixd.log 中 provider switched / in-place retry / gave up 关键词归组——失败被编排层重试/换道救回的过程性消耗。

条目引导：中途信号作为 waste / improvements 的证据来源，量化离群与停滞可直接立项（如「成功 run 的 45 轮里 X 轮停滞 >60s」）；深扫行首条 error/stderr 摘要与救回痕迹样本可交叉核对第 2 节 runs 统计定位具体 run。中途信号不产生告警，只作证据；引用时同样遵守「含证据/含调查评估」质量标准。

### 闭环判定（存在「近 3 日既有条目」时）
对上方既有条目逐条判断：该问题**是否已经被修正**（如对应 fix 已提交、SPEC 已落地、告警/错误不再复现）。判定依据 MUST 可核实（commit hash、spec 名、告警 id 等），必要时只读查看 git log 与源码核实；拿不准的保守起见**不判定**。已修正条目写入回顾 JSON 的 `resolved` 数组（id + reason），daemon 会将其从 todo.md 移除。

## 铁律（MUST NOT）
1. 只产出回顾，**禁止**创建任何 SPEC（不写 spec/changes/、不注册 .fenix/STATE.md 条目）。
2. **禁止**派发任何 implementer/verifier/planner agent，不修改框架代码。
3. 不要修改 .fenix/STATE.md、tasks.md 或任何源码文件，你的唯一产物是下面的回顾 JSON。
4. read_todo=true 时：判定已闭环的历史条目**不再重述进新节**，改写入 `resolved`（闭环判定）；仍存在的历史条目在重述时标注「（新增）/（恶化）」。
