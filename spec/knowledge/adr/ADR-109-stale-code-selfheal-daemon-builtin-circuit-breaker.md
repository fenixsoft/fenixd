# ADR-109：代码陈旧自愈由 daemon 内建闭环，外部脚本退役

date: 2026-09-18
status: accepted

## Context

自我开发项目里 daemon 持启动时刻代码副本是常态。检测侧早已完备（30s mtime 指纹、worktree 友好），动作侧缺失——命中后只 WARNING 一次即永久静默；空闲重启能力其实存在但接错线：挂在外部 hook 脚本、绑死单个 SPEC 的 done 事件、靠 ps 特征串反推活跃 run。

## Decision

- 陈旧是 daemon 自维护的持续状态：既有 30s 检测节拍重算陈旧标志并驱动告警与自愈，移除「每进程只提示一次」旗标——「我跑的是不是旧代码」只有进程自己能回答，状态不外置给脚本。
- 空闲判定用内部状态双源：agent_runner 零活跃 run **且** admin 处置线程池无在途任务（admin 走独立池，不反映在活跃 run 上）；不用 ps 扫描——看不到已入队未派发的 run、依赖命令行特征串、失败只能永不重启。
- 单一实现路径：空闲重启内建进 daemon，外部 when-idle 脚本与其 hook 挂载一并删除——两条路径的空闲口径不同（内部状态 vs ps 特征串），并存必然产生「脚本说要等、daemon 说可以重启」式分歧。
- 自愈以消费链完整为前提：项目未被 supervisor 托管时不写 restart_request、只维持陈旧告警——断链时制造「已安排自愈」的假象（死信挂 12 小时无人消费）恰是事故形态。
- 启动熔断：60s 内退出计一次启动失败，连续 3 次停止自动拉起并写熔断标记 + critical 告警，人工修复后清标记；不做 half-open 自动重试——坏代码不会自愈，自动重试只会延长故障展示。
- 配置默认开启且必须带界面；陈旧告警 warning 级（可经空闲自愈收敛、不占人工队列），按状态边沿触发不堆积。

## Consequences

- 「改代码 → 空闲 → 新代码生效」自动闭环；残留风险是「能启动但行为错误」的新代码，熔断不覆盖，靠告警与日志事后追溯。
- 启动熔断阈值与 supervisor 停止路径宽限常数语义相反（判定启动成败 vs 停止宽限），不复用同一常数。
