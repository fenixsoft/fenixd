# 工具调用效率治理

长车道提示词中的工具调用效率与取证深度约束：批量并行、定向读取、同 run 去重、最小可判反证与输出裁剪。

## 现行规则

- 注入范围：「工具调用效率」契约段注入实现者（`implementer` / `fast-track`）与评审（`spec-review`）车道的 prompt。
- 批量并行：同一轮内相互独立、无数据依赖的工具调用（多个读取/检索）合并为一个批次一次性提交，不逐个串行提交。
- 定向读取：定位代码或内容优先用 `Grep` / 带范围参数的 `Read`，不对未发生变更的大文件反复整文件读取。
- 同 run 去重：同一 run 内已读取且未变更的文件不重复整文件读取；需复核时用范围读或检索。
- 取证深度上限：取证以「足以判定结论的最小可判反证」为限——评审车道在判定 `blocking`（前提被证伪）vs `repairable`（文档内可修）所必需的最小证据之外，不穷尽复现 SPEC 声明的全部断言；实现车道不为「完整复现」重复重跑全量套件。
- 输出裁剪：可能产生大块输出的命令（探针/日志/构建）先裁剪再入对话——`head -c`、只取关键行、或落临时文件后只回读关键片段；不将数十 KB 原始输出整块投入对话上下文。
- 纯提示词层：以上约束不引入框架侧工具拦截、命令改写或流式处理时序改动；段注入位置不破坏既有契约段顺序断言。
