# ADR-048：admin 处置车道并发模型——主循环只投递，线程池执行，处置文件按实例分离

date: 2026-09-08
status: accepted

## Context

主循环同步调用 admin run，阻塞至处置完成（实测单次数分钟，dashboard 呼叫后拾取延迟最高 231 秒），期间 SPEC 派发、巡检、后续信号拾取全部停摆。处置状态文件为全局单文件，并行实例互相覆盖。Administrator 的资源模型为主树直操作（不建 worktree，用户决策容忍写冲突风险）。

## Decision

- 主循环对 admin 呼叫信号只做「读文件 → 删文件 → 校验 → submit」，处置后台化；后台执行用线程池而非子进程——runner 上下文跨进程序列化复杂度高且无收益，GIL 对阻塞式子进程等待与文件 IO 无影响。
- worker 函数体 catch-all，单次处置异常不退出线程池；落痕语义（pending → final → failed disposition）保留在 worker 路径。
- 处置状态文件按 run 实例分离：`.fenix/admin_disposition-<run_id>.json`，写入路径注入提示词，读写函数参数化路径；旧全局路径退役。
- worker 数可配（默认 2），0 = 回退同步行为（逃生门）；主树并发写冲突由用户决策容忍（处置多为只读诊断 + 收尾单次 commit），实现不做主树互斥，出现实际踩踏再引入轻量串行。

## Consequences

- 通用纪律成立：主循环内的任何文件信号拾取路径都不得同步执行长任务，拾取与执行必须解耦。
- 实例文件在 run 异常中断时可能残留，无功能影响；拾取新请求时顺带清理超期残留。
- 主循环阻塞类问题的形态从「单点卡死全部」变为「池耗尽排队」，池大小成为新的容量旋钮。
