# ADR-200：手动触发受理回链不承载 run 终态，受理窗口守卫凭 run 标识 epoch 构造性区分排队与已跑完

date: 2026-09-29
status: accepted

## Context

文件信号 + 异步消费的手动触发链路（code-fix、code-review）存在受理→运行窗口：POST 200 只是信号落盘，daemon 经主循环拾取、线程池排队、manifest 收集后才创建 run，窗口内进度判据恒 false。用户在该窗口得不到任何反馈（唯一兜底是周期心跳），且第二次 POST 能同时通过 running 守卫与信号独占守卫返回 200，随后被 daemon 单飞静默丢弃——假受理。

治理方案是结果回链文件（三态 started/dropped/failed）+ POST 受理窗口守卫。但回链文件只承载受理判定、不在 run 结束时回写终态（worker 在 run 完成后无任何结果文件写入），于是「`status=started` 且 `progress.running=false`」形态二义：「排队收集中」与「已跑完」完全相同。仅凭新鲜度窗口，run 结束后窗口内的合法重触发会被假 409「正在启动」拒绝，相对既有立即放行行为属回归。

## Decision

1. 结果回链文件单文件覆盖写，只承载受理判定三态，不在 run 结束时回写 run 终态；run 是否已启动过不由结果文件承载。
2. 受理窗口守卫必须以构造性判据消除上述二义：run 标识内嵌 epoch（run_id 形如 `code-review-<epoch>[-<n>]`）大于结果 `finished_at` 即「受理的 run 已启动并结束过」→ 放行；`finished_at` 距今超新鲜度窗口（900s）→ 放行，防陈旧结果永久锁死触发。两条判据缺一即引入「假 409 锁死」或「陈旧结果误拒」回归。
3. POST 200 只代表信号已写，不构成启动确认；前端以 `requested_at` 回链匹配本次触发，陈旧残留结果不作本次反馈。
4. 守卫读竞态与超窗放行统一 fail-open 到 daemon 单飞的显式拒绝并落结果文件——链路终点必须是有反馈的显式拒绝，禁止静默路径。

## Consequences

- 结果文件无历史留存，消费端每次消费新信号即覆盖旧结果；正确性完全依赖 `requested_at` 回链匹配，不依赖结果文件时序。
- 后续车道复用受理回链模式时必须同时复制 epoch 构造判据与新鲜度窗口；只抄三态落盘不抄判据会引入回归。
- 误放行的代价由既有守卫吸收（running 409 或单飞 dropped 落结果），窗口守卫本身允许保守放行。
- 前端等待态两段上限（等结果 120s、等启动 60s）超时解禁后重复触发，由窗口守卫或单飞显式拒绝，不会重复执行；run 仍可能稍后开始，由既有周期心跳兜底。
