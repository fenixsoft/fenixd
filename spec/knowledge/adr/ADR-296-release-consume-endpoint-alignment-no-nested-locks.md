# ADR-296：失败登记解除与核销终点对齐——出册必接手核销、在册零核销，跨文件对齐禁双锁嵌套

date: 2026-10-30
status: accepted

## Context

达重试上限的失败批有三类终局产物：fix-failed.json 注册表记录、`code_fix_retry_budget_exhausted` 告警、todo.md 人工排查登记块。核销对账（consume_resolved_failed_batches）按注册表记录驱动——记录被删除即永远够不着对应登记块。人工整批解除（release_failed_batch）曾整批删除记录且函数体零 todo 引用，「已解除但未核销」的登记块成孤儿，登记正文还可能在无人核销的窗口内损毁成裸标题壳，人工连排查线索都没有。两条生命周期终点（解除与核销）此前无交接契约；同时 todo 锁与 fix-failed 锁是两把独立锁，「同一锁内对齐」字面不成立。

## Decision

失败登记的两条生命周期终点必须对齐，核销归属按记录是否出册分岔：

- **出册必接手核销**：任何使注册表记录出册（整批删除）的解除路径，MUST 在删除成功后的同一调用序列内 best-effort 核销 todo.md 对应登记块——记录出册后 consume 对账按注册表驱动永远够不着该登记块，同步核销是其唯一核销时机，错过即成孤儿。
- **在册零核销**：记录仍保留在册的解除形态（部分解除收缩、预算内自动释放的打标墓碑 `released=true`）MUST NOT 触登记块——在册记录由 consume 闭环天然覆盖，且预算内记录未达登记阈值本无登记块；强行接入无条件核销会在预算分档漂移时提前抹掉仍在跳条目的人工排查登记。
- **禁双锁嵌套**：跨文件对齐不做锁嵌套（嵌套引入锁序风险），以同调用序列 best-effort + 留痕审计兜底——fix-failed-release.jsonl 留痕行必须携带 todo 块处理结果（consumed/not_found），崩溃窗口最坏退回「已解除未核销」，必须可事后审计。

后续任何新增「记录出册」路径（脚本化清理、批量退役等）同受此契约约束：出册动作必须同点接手登记块核销，或显式并入既有解除入口。

## Consequences

解除与核销不再有孤儿窗口：整批解除即干净收尾；部分解除与自动释放的登记生命周期仍由 consume 闭环单点收口，核销动作不存在双写者。代价是解除主流程挂上 best-effort 的 todo 写（失败仅残留可审计的 not_found，不阻断解除语义与重试预算）；留痕行成为解除审计的唯一对账面，改留痕结构必须同步消费侧。若未来出现「记录出册但 consume 语义改按非注册表源驱动」的新形态，本裁定出册分支须重新评估，推翻须显式 supersede。
