# ADR-228：手动 LLM 健康探测=后端无状态代理纯探测，与运行期熔断状态隔离

date: 2026-10-04
status: accepted

## Context

Provider 配置（Base URL / API Key / 模型名）是否真正可用，此前只能等下一次 agent 派发失败才知道，排障链路太长，需要一键健康检测。落点上有两个架构级风险必须先裁定：其一，浏览器直连任意 baseurl 受 CORS 限制，且 API Key 会暴露给页面运行时之外的网络路径；其二，探测结果天然贴近运行期故障治理——若探测写入 provider 4xx 熔断计数、切换冷却或半开探针状态，用户一次手动点检就能把 provider 打入冷却，误伤在飞派发。

## Decision

对外探测一律由 daemon 后端代理执行，浏览器不直连第三方 baseurl。探测端点保持无状态、入参显式三字段（baseurl/apikey/model），provider 双源解析与模型解析链等作用域逻辑全部在前端完成，端点不隐式依赖配置作用域。探测为纯只读：不落盘密钥与完整响应，MUST NOT 写入运行期熔断体系的任何状态（熔断计数/切换冷却/半开探针），手动检测与运行期熔断彼此隔离。探测请求签名与运行期 claude CLI 同构（同 `/v1/messages` 路径同协议同 UA 头），保证「检测通过」对「运行期可用」有效。

## Consequences

探测结论可信代表运行期可用性，手动点检零副作用、不可能污染熔断治理；端点可单测（monkeypatch urlopen）、无配置作用域耦合。代价是解析链逻辑落在前端（表单/已保存双源解析），后端对 provider 名不可见；同步端点占用 handler 线程最长 15s（依赖 dashboard 既有并发线程模型，不做异步化）；后续任何新增探测类能力（如自动巡检）都必须沿用「后端代理+无状态+不触熔断状态」三件套，不得顺手复用熔断记账通道。
