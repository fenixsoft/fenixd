# ADR-312：冻结装载读端接入场景拯救——接入判据改时序暴露面

date: 2026-11-02
status: accepted

## Context

ADR-286 裁定场景顶层 dict 包裹拯救只接验收归因单点、全部读端零防御恒假设纯数组顶层，依据是「拯救原子重写落地后其余读端按既有语义自然恢复」。该恢复假设隐含时序前提：读端读取发生在拯救落地之后。2026-10-26 add-command-center 冻结事故证伪了该前提对冻结装载读端的适用性：verify agent 写出 dict 包裹形态后，冻结装载读端在验收归因点运行之前就读入文件，顶层非数组 fail-closed 直接触发场景计划争议，连续 2 轮自动冻结转人工，16/18 pass 的真实验证成果作废——「自然恢复」对时序在拯救点之前的读端不成立，同一包裹形态出现「验收归因点能救、冻结读端炸冻」的一救一炸分裂。

## Decision

- 拯救实现保持单源（`_salvage_top_level_dict`，内部即 `salvage_scenarios_file`）：冻结装载读端直接调用既有实现，不写第二份解包实现；拯救返回的列表直接作为顶层内容继续既有冻结契约迁移与装载（文件已被原子重写为纯数组，内存与磁盘一致）。
- 读端接入判据由「一律不接」修正为「时序暴露面」：读取时序可能先于既有拯救点的读端必须自带拯救接线；时序在拯救落地之后的读端维持零防御、恒假设纯数组顶层。冻结装载读端属前者，`load_scenarios` 本体、fastlane、verdict_evidence 等属后者，后续新增场景文件读端按此时序判据归类。
- fail-closed 语义不动摇：解包不可拯救（缺 scenarios 键、解包后条目仍非法、原子重写失败，含异常兜底）一律落回既有 corrupt → env_blocked 人工通道，与无拯救时逐位一致；解包留痕沿用 ADR-286 口径（WARNING 记顶层键与条目数，不新增日志形态）。

## Consequences

- 防御面由验收归因单点扩为「验收归因点 + 冻结装载读端」两点，仍收敛于单源实现；读端是否接拯救不再逐案争论，按读取时序机械归类。
- 冻结轮对 dict 包裹自愈：16/18 pass 一级的真实验证成果不再因顶层包裹形态被整轮作废。
- 代价是冻结装载路径多一次分支判断与解包重写窗口；该窗口与验收归因点既有重写竞态同级，且验证轮内冻结装载与场景消费不并发。
