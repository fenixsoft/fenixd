# ADR-383：子代理扇出治理走提示词契约与终态标记接力，与 provider/run 级 429 防线两层正交

date: 2026-11-27
status: accepted

## Context

审查/修复 run 的子代理由 run 主体（claude CLI Task 工具）自行派发，框架代码不在派发路径上——既不校验在飞数也无 429 感知；在飞上限只是注入提示词的文本契约。全部既有 429 防线（provider_circuit 冷却、终局重派登记、error 收场抢救、分片续跑）都在 run 终态/provider 级，run 主体存活期间子代理死亡不落任何防线。账户级 429 事故反复（2026-09-24 两波并发打死账号 43 分钟、code-review-1790574672 死于 429 全量重烧约 14 美元、2026-11-24/25 两晚各死 3 子代理且单 run 成本推高到 $19-20、admin 告警零落账），需要裁定：run 内扇出治理放在哪一层、如何观测。

## Decision

- **行为面走提示词契约**：429 记忆、退避与止损规则写入 `agents/code-review.md` / `agents/code-fix.md` 由 run 主体执行，框架不做进程内节流器——派发不经框架代码，进程内节流无处安放；契约条款沿「违反 = run 判失败」既有语义执行。
- **观测面走终态标记两段接力**：run 主体仅在完成统计行末追加标记（`[review_429_storm=true; failed_shards=<n>]`——统计行是 run 主体终态输出的唯一固定锚点，不另写 sidecar 文件，产物与分片写路径契约不动），框架收尾解析标记回填结果信封字段，admin_monitor 沿既有 getattr 意图消费模式产生告警；run 主体漏报时字段保持缺省，降级为无告警、零假阳性。
- **两层正交**：provider_circuit 与配额重置派发冻结管「该不该派这个 run」，扇出层管「run 内派多少子代理」；本裁定不做 per-provider 429 时点持久化记忆，避免两层重复建设。风暴告警与 run 级 ratelimit_redispatch 终局重派按 run 终态天然互斥（run 被打杀时风暴标记无从产生）。
- **跨 run 记忆以归档 jsonl 尾窗扫描实现**：上一轮同车道 run 存在 429 终态子代理死亡则本次注入上限折减至 1，扫描缺失/异常 fail-open 按原配置放行；告警计数与记忆折减允许低估（宁可少报不误报，不做全量扫描控制收尾开销）。

## Consequences

- 契约条款依赖 run 主体遵从、无硬闸——接受：与模板既有条款同级；风暴告警提供观测兜底。同题双 SPEC 的退避规则 MUST 单段收敛（并存时按更严格者执行），MUST NOT 两套互斥间隔并存使 run 主体无所适从。
- 静态缺省降档（4→2）拉长全仓审查墙钟——接受：4 并发在账户级 429 面前是伪吞吐（秒死重派 + parent 接管补审的隐性成本更高）；显式配置可调回；一键两用的 ocr scan 缺省并行度同步降档属声明内接受面。
- 后续任何触及子代理扇出的治理沿同一形态扩展（提示词契约条款 + 终态标记/结果信封字段接力），不在框架侧新增派发强制点；跨项目审查排程协调不做排程系统，仅以告警提示错峰，实际复发再立项。
