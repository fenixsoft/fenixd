# dashboard-spec-table Spec（delta）

## MODIFIED Requirements

### Requirement: SPEC 行提供「文档」链接（整合原「背景」「设计」按钮）

系统 SHALL 将 SPEC 列表页（项目视图）每一行文档操作列中原「背景」「设计」两个按钮整合为单个「文档」超链接。该链接 SHALL 始终可见（不要求任何文档文件存在），点击 SHALL 打开三页签文档弹窗（见「文档弹窗展示」要求），且 SHALL NOT 触发行级跳转（进入详情页）的既有交互；点击行其余区域 SHALL 保持原有跳转行为。原两个按钮及各自独立弹窗入口 SHALL 随本要求移除。

#### Scenario: 每行显示单个文档链接
- **WHEN** 打开项目视图，某 SPEC 行正常渲染
- **THEN** 该行文档列显示一个「文档」链接（不再显示「背景」「设计」两个按钮）

#### Scenario: 点链接打开弹窗且不进入详情
- **WHEN** 点击某行的「文档」链接
- **THEN** 弹出三页签文档窗口，页面 URL 不变，未跳转到 SPEC 详情视图

#### Scenario: 点行空白区域仍进入详情
- **WHEN** 点击该行非链接区域的空白处
- **THEN** 跳转到该 SPEC 详情视图（既有行为不变）

### Requirement: 文档弹窗展示（三页签）

系统 SHALL 在点击「文档」链接时于当前页弹出模态窗展示该 SPEC 的三份文档，窗口内含三个页签：「需求背景」/「详细设计」/「任务清单」，分别对应加载 `proposal.md`、`design.md`、`tasks.md` 原文并渲染。标题 SHALL 包含 SPEC 名称。正文 SHALL 以 Markdown 渲染（复用既有 `marked` 渲染管线，支持 GFM 语法，执行既有链接白名单与转义约束）。页签内容 SHALL 按需加载：打开窗口默认激活「需求背景」页签并加载；切换至另一页签时若该页签尚未加载 SHALL 发起对应请求并显示加载占位，已加载则直接展示缓存内容。弹窗 SHALL 支持通过关闭按钮、点击遮罩关闭；加载期间 SHALL 显示加载状态；打开期间 SHALL 不阻塞列表页状态，关闭后列表页保持原状。

#### Scenario: 打开弹窗默认显示需求背景
- **WHEN** 点击某 SPEC 的「文档」链接（该 SPEC 的 proposal.md 存在）
- **THEN** 窗口打开，「需求背景」页签激活并展示 proposal.md 渲染后的 Markdown 内容（标题变粗、列表带符号、代码块等宽），标题含 SPEC 名称

#### Scenario: 切换到详细设计页签
- **WHEN** 弹窗打开后点击「详细设计」页签（design.md 存在）
- **THEN** 激活该页签并展示 design.md 渲染内容；切回「需求背景」不再发起新请求（已缓存）

#### Scenario: 切换到任务清单页签
- **WHEN** 弹窗打开后点击「任务清单」页签（tasks.md 存在）
- **THEN** 激活该页签并展示 tasks.md 渲染内容（含任务勾选状态原文）

#### Scenario: 加载与异步失败
- **WHEN** 点击页签后请求未返回时显示加载占位；请求失败（非 200/404、网络中断）
- **THEN** 该页签内显示错误提示，不显示空文档

### Requirement: 文档缺失空态（页签级）

系统 SHALL 在该 SPEC 的对应文档文件不存在时，于对应页签内展示明确的空态提示（如「该 spec 未提供需求背景/详细设计/任务清单文档」），而非空白或报错。「文档」链接与各页签在文档缺失时 SHALL 保持可见可点。

#### Scenario: 缺失文档显示页签级空态
- **WHEN** 某 SPEC 没有 design.md，点击「文档」链接后切到「详细设计」页签
- **THEN** 弹窗正常，该页签正文显示「该 spec 未提供详细设计文档」一类空态文案，其余两页签不受影响

### Requirement: SPEC 信息子行（信息标签与内容同行 + 清除按钮）

系统 SHALL 保持「当某 SPEC 的 `STATE.md` 条目 `error` 字段非空时，在该 SPEC 行正下方渲染跨全部列宽的信息子行」行为不变，但 SHALL 满足以下改动：

1. **标签与内容同行**：「信息」标签与其消息内容 SHALL 渲染在同一行（中间无换行，无论消息长短）；仅消息自身文本内含的换行符按原样保留。信息较长时正文 SHALL 独立换行不破坏表格宽度。
2. **清除按钮**：信息子行 SHALL 在行尾提供「清除」操作按钮；点击 SHALL NOT 触发行级跳转。点击后调用 `POST /api/spec-error-clear?project=<name>&spec=<name>`，成功后将该项目 `STATE.md` 中该 SPEC 的 `error` 字段置空（原子写回，不改动其余字段），随后列表经既有 2 秒轮询/SSE 机制刷新后该信息子行 SHALL 消失。清除为当前快照操作：Agent 或恢复流程后续若再次写入 `error`，信息子行 SHALL 重新出现。清除过程中网络失败 SHALL 在按钮旁或行内给出失败提示，不产生误导性的成功感。

该消息为空或 `null` 时 SHALL 不渲染信息子行（不占行高）；现有过滤、排序、自动刷新行为 SHALL 保持不变。

#### Scenario: 标签与内容同一行显示
- **WHEN** 某 SPEC 的 `error` 字段为短消息（如 `Recovered from interrupted state`），打开项目视图
- **THEN** 信息子行中「信息」标签与消息文字显示在同一行（无标签后的独立换行）

#### Scenario: 长消息可读不破表
- **WHEN** 某 SPEC 的 `error` 字段为含内部换行的长消息，打开项目视图
- **THEN** 信息子行「信息」标签与消息首段同行，消息内部换行保留、长行自动换行，不破坏表格整体宽度

#### Scenario: 清除按钮置空 error 字段
- **WHEN** 某 SPEC 存在非空 `error`，点击其信息子行行尾的「清除」按钮
- **THEN** 请求 `POST /api/spec-error-clear` 返回成功，该项目 `STATE.md` 该 SPEC 的 `error` 字段变为 `null`，其余字段（status/priority 等）不变；列表刷新后该信息子行消失

#### Scenario: 点击清除不触发详情跳转
- **WHEN** 点击信息子行的「清除」按钮
- **THEN** 未跳转到 SPEC 详情视图，仅执行清除操作

#### Scenario: 清除失败给出提示
- **WHEN** 点击「清除」后端点返回错误（如项目已删除、网络中断）
- **THEN** 界面显示清除失败提示，信息子行保持显示，`STATE.md` 未被修改
