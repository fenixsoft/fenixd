# 挂起与慢速判别（实质事件/心跳分离）

活性快照把 run 流事件分为实质事件与心跳两类并分离计数，为停滞判定提供不失真的进度口径。

## 现行规则

- 事件二分：**实质事件**为 `assistant`（工具调用/文本）、`user`（tool_result）、`result` 等承载任务进展的事件；**心跳**为 `tool_progress` 等仅表明「进程仍在等待/存活」的周期性事件（无时间戳、按 `elapsed_time_seconds` 递增）。一切「是否在推进」的判定以实质事件为依据；心跳不计入「窗口内有新事件」的进度证据，不作为 advancing 的依据。
- 仅心跳流入的窗口不得判为推进；窗口内实质事件数为零时走「窗口内零事件即判停滞」守卫，心跳持续写入不得使该守卫失效。
- 快照分离计数：`substantive_events_in_window`（窗口内实质事件数）、`tool_completions_in_window`（窗口内完成的工具调用数，即 tool_result 数）、`heartbeats_in_window`（窗口内心跳数）；证据摘要三者同时呈现，不得只给一个混合的「事件数」。
- 停滞的确定性短路仅限「可观测零产出」情形：run 在窗口内阻塞等待某后台调用（长时 `TaskOutput`/背景命令）不短于固化阈值、该后台调用关联输出文件可观测且窗口内大小零增长、窗口内工具完成数低于固化阈值——三者同时成立时方可不经判定 LLM 直接判停滞；判定须标注为启发式「零产出」判定（与 LLM 判定及其他短路原因文案可区分），并记录后台调用标识、输出文件路径与零增长区间。任一条件不成立（尤其输出文件不可观测）时必须走既有 LLM 判定路径，不得短路。
- 明确排除的判据：不得以「重复相同工具调用占比」或「工具结果文本重复度」作为停滞判据——合法长跑 run 的重复度可能更高，以高阈值为阈永不触发、下调到能触发则误杀合法 run。
