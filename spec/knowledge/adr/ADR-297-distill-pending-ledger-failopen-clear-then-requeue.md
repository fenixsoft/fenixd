# ADR-297：蒸馏 pending 台账 fail-open 侧记、恢复先清空后入队

date: 2026-10-30
status: accepted

## Context

蒸馏批次状态原为纯进程内内存态，daemon 重启即蒸发，多次实锤造成入库断流：批次滞留主树靠散件巡检事后兜底（消耗 admin run），部分批次零产出零台账、知识彻底丢失。需要把「在飞批次」持久化并在重启后续跑。但台账若按事务队列实现（跨进程锁、先入队后清空、读损坏即阻断派发），会把毫秒级入队变成归档主流程上的关键路径——归档是高频操作，台账自身的故障不能反过来阻断归档；且恢复重派与台账写点共用同一咽喉，恢复顺序选错会自己抹掉刚落盘的条目。

## Decision

pending 台账是 best-effort 侧记而非事务队列：写入点收在 dispatch 单一咽喉（持进程内 guard 的单写者，整文件重读-改-原子回写），与 flock 单飞不同文件、互不阻塞；读缺失/损坏/形态不合规按空表 fail-open——宁可丢台账退回内存态现状，不阻断归档与派发。恢复顺序 MUST 为「先清空台账文件、后逐条经门控链重新入队」：恢复重派本身会经写点立即重新落盘，若先入队后清空会把刚重写的条目一并抹掉，恢复 run 期间台账裸奔（此时崩溃即重演丢失）。恢复动作只重新入队、不执行蒸馏（实际 run 走既有 flock 单飞与 worker 串行消费），入口仅 daemon 启动路径接入（dashboard --serve 不做恢复，跨进程竞争由此规避）；清空与逐条重派之间的毫秒级残差窗口与读损坏同口径接受，不为该窗口引入跨文件事务。

## Consequences

台账生命周期与批次收尾对账绑定：成功收尾/清理确认后移除，「提交失败/执行异常/回滚未确认」滞留路径保留交重启续跑，崩溃恢复语义收敛为「收尾前始终在册、重启即可再恢复」。代价有三：① 台账互斥仅进程内，dashboard --serve 与 daemon 并发派发存在整文件覆盖丢条目窗口（后果等同台账丢失，按 fail-open 接受）；② 恢复的先清空与逐条重派之间有毫秒级残差窗口；③ 空闲判定（陈旧自愈）的蒸馏维度只能看进程内活体状态（worker 线程/队列），盘上台账存在不构成在飞证据——死台账不钉住自愈。后续给台账加跨进程事务、以盘上文件判蒸馏在飞、或让 dashboard 进程接入恢复，均须显式 supersede 本裁定。
