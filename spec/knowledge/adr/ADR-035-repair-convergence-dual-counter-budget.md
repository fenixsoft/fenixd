# ADR-035：修复收敛双计数器——轮数 PASS 单点归零，实现 run 总预算设卡

date: 2026-09-06
status: accepted

## Context

升级闸门「连续 3 轮验证失败找人工」的语义是连续失败，但打回重派/修复收工路径上的整体字段更新连带把 `_verify_fail_rounds` 归零，「修→验→修」每个局部循环都被当成新一轮，闸门永不触发。同时 run 级 max_retries 只约束单次派发的 attempt，跨修复轮无总量概念，重灾 SPEC 可无限消耗实现 run。

## Decision

- `_verify_fail_rounds` 全仓唯一归零点 = 验证 PASS 采纳处；打回重派、修复收工路径不得触碰。run 级 `_retry_count`（attempt 计数）语义不同，用字段级更新与轮数计数隔离，避免连带覆盖。
- 实现 run 总预算 `_impl_run_budget_used` 在 implementer 派发时递增并持久化（跨重启有效）；设卡点在重派决策处（打回重派、失败重试重派）：`used >= agents.impl_run_budget`（缺省 4，可配 1-10，配置键带 Dashboard 界面）→ blocked + 告警（`impl_budget_exhausted`）。
- 已启动的 run 正常跑完并 merge——沉没成本不浪费，只是不再自动开新一轮。
- 预算耗尽与 3 轮冻结同构：blocked + 既有升级告警通道，人工改计数/预算或直接推进状态即可解冻，不新增人工流程。
- 两个计数器语义分立：验证轮数管「修不好」（连续性），实现预算管「修不完」（总量）；报告中分列展示，告警分别措辞。

## Consequences

- 「连续修不好」与「修不完」两种失败模式各自有界，闸门真正可达触发。
- 首次实现也计入预算，重灾 SPEC 的修复空间为 3 轮量级——与验证闸门一致的收敛压力，是有意取舍。
- 双计数器并存有心智负担，由分列展示与措辞区分缓解；复杂 SPEC 预算不够时人工调大即可，代价可控。
