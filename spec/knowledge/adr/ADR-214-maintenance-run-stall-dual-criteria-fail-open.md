# ADR-214：维护型 run 停滞判定双判据合取，判据不可用 fail-open

date: 2026-10-03
status: accepted

## Context

周期审查 run 出现「网络僵死但进程活着」形态（实测 2h20m 仅 49s CPU），把 code-fix 车道绑死 90 分钟才被人工取消。对这类有进度产物的维护型 run，单 mtime 判据会被「进程活着空转、产物不再更新」形态漏判之外，还会把「进程活着且在推进、产物恰好暂不可读」的正常 run 反复清零停滞计时；单 CPU 判据则会误杀长时间等 IO 的正常 run。两条单判据路径各有系统性盲区。

## Decision

维护型 run（周期审查等有进度产物的后台 run）的停滞判定固定双判据合取：进度产物最新 mtime（主产物 + 全部分片）与 run 子进程进程树 CPU 时间，两者同时无进展才计停滞；任一判据有进展即整体重置计时。判据不可用一律 fail-open 不触发：CPU 不可解析（进程句柄缺失/已退出）不触发——此时取消原语也无从终止；产物暂不可读沿用上一轮读数，既不算进展也不清零计时。阈值独立成配置键（`admin.review_stall_minutes`，缺省 30），缺失/非法/非正整数回退缺省，巡检路径不因脏配置中断。达阈值动作复用既有取消原语与急救落账路径，不新造落账通道，告警单 run 去重。

## Consequences

- 僵死 run 在有界时间（阈值 + 巡检节拍）内被自动收走，车道不再被连坐，无需人工取消 + 重启。
- 误杀面仍存在（慢而健康的 run 可能被收走），兜底为急救落账无损 + 手动重审一次；误杀概率由「任一判据有进展即重置」与 30 分钟缺省压低。
- 后续新增维护型车道若需停滞看门狗，MUST 沿用双判据 + fail-open 口径，禁单判据短路、禁因单判据读取失败而触发。
