## 背景

全仓夜间代码审查（code-review 车道）由父 run 派 Task 子代理批次执行，批次产物直写落盘为分片，收尾时既有守卫 `_writeoff_coverage_guard`（core/agent_runner/maintenance_runs.py:2892）已按「分片+主产物」权威口径对 manifest scope 做覆盖对账。2026-11-21 夜审（code-review-1795190463）实测：该守卫算出覆盖 311/362（真缺口 51 文件、14.1%；分片单口径差集 79 文件、21.8%）并落 WARNING「维持抢救红线，不核销」，但对账无执行面——run 终态仍记 success、零告警、不落 writeoff 锚、不触发续审。缺口只能靠次夜全量审查兜底（延迟约 24 小时），当轮 $109.79/2.08h 的审查价值缩水约 14-22% 且不可见。

## 根因（已裁决）

- 父 run 批次计划结构性偏短：档案中 Agent tool_use 恰 34 次，分片批号不连续（缺 b8/b11/b14/b15/b18），而已派出的批次每个都有分片落盘——排除子代理静默死亡与派发失败未留痕两假说。可确证的事实是 34 个批次分片合计仅覆盖 311/362 文件（真缺口 51 文件）；「缺号＝曾计划但未派发」目前只是推断——批号由 agent 自选，框架侧不存在批次派发逻辑（分批完全由 agents/code-review.md 授权 agent 自主决定），故本 SPEC 同时补「计划声明 + 收尾对账」使该形态可直接判定（见 design 改动点 2）。批次计划偏短属模型行为，任何一夜可再现。
- 干净收尾形态无兜底触发面：writeoff 锚写入门仅重启旗标/排水路径可达（maintenance_runs.py:3416），error 抢救锚仅 error 收场可达（:3560-3581）；本窗为无打断的 end_turn 干净收尾，锚路径结构性不可达，锚续审扫描（core/admin_monitor.py:2933）因无锚即返。
- 在途 SPEC evo-drain-inflight-run-protection 的触发面为重启旗标+error 收场，不含本形态——属既有守卫与锚机制的执行层缺口，非重复立项。

## 目标

覆盖缺口超阈值时不再静默记 success：终态降格、告警留痕、落 writeoff 锚使既有续审扫描自动武装 redispatch；批次计划侧补声明与收尾对账（agent 先落批次计划、框架收尾对账），使计划偏短形态可直接判定。

## 非目标

不改变排水硬杀/限流终局续跑等既有触发面；不改变「分片+主产物」覆盖口径；低于阈值的常规小缺口（如前夜 0.6%）保持现行为（WARNING 留痕、success 终态）。
