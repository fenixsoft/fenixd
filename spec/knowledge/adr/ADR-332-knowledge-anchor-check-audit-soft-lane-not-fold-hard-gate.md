# ADR-332：代码锚点存活检查走 audit 软档、不进折叠硬门

date: 2026-11-08
status: accepted

## Context

能力页新增「代码锚点」段后，锚点会随代码移动而腐化——agent 敢不敢信任锚点，取决于腐化能否被机械暴露。锚点修复需要语义判断（定位新位置），机械自删会丢信息；而蒸馏折叠的前置校验 validate_knowledge 跑全树，若把锚点悬空放进硬门，一处陈旧锚点就会把内容问题放大成整条折叠管线的阻塞。

## Decision

锚点存活检查独立为 `check_anchor_references(project_root)`，扫描面只限能力页 `## 代码锚点` 段内的路径 token（段内 `路径:行号` 尾形态报「行号必腐」格式违规，与悬空并列两类发现；`spec/archive/`、`spec/knowledge/_inbox/`、`node_modules/` 前缀豁免），不做全页启发式——精确、零误报、无排除名单负担。消费面固定走 audit 体检车道（病灶⑥），悬空与格式违规进体检报告「待人工/定向转写」档计数与明细。两道纪律边界：**不并入 validate_knowledge 硬门**（内容病灶不得阻塞全树折叠校验）、**不机械自删悬空锚点行**（修复需语义判断，处置走定向转写或人工）。

## Consequences

锚点腐化由每日体检稳定暴露，agent 可信任「体检报告病灶⑥零悬空时锚点是活的」；代价是悬空锚点的清除非即时——从文件移动到下一轮体检处置之间存在窗口，期间锚点可能失准；后续内容质量类检查沿用同一分层先例：机械可判且可自修的进硬门与自修车道，需语义判断的进体检报告待处置档，另立硬门或自删车道须显式 supersede。
