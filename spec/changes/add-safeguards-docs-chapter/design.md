# 设计：帮助文档「保障机制」专章

## Context

docs/help/ 现有 10 章 + README，按使用场景编号。机制相关的既有覆盖只有两处：06 章「调度与治理规则」写了预算三类、重试退避、超时监督、自动恢复、告警分级**流向**等运维口径；10 章 FAQ 按现象反查根因。机制本体（lint 规则是什么、硬门在哪一步拦、守卫对账什么、自愈链路怎么触发、告警为什么这么分级）没有任何一章从设计视角系统讲过。机制实现散布在 `core/deliverables.py`（声明 lint/收工守卫）、`core/pm_engine/promotion.py`（晋升 lint）、`core/verdict_check.py`（产物硬门）、`core/state_machine.py`（转移门/frozen）、`core/verify_engine/env_gate.py`（环境门）、`.fenix/hooks/`（PreToolUse 拦截与出题分批）、恢复/清扫/watchdog/重启协议等自愈链路、`core/alert_lifecycle.py` 与 `core/admin_monitor.py`（告警生命周期）——盘点必须回到代码，不能凭记忆写作。

已确认的用户决策：章节**插入为第 07 章**（06 章之后，原 07–10 顺延为 08–11）；与 06 章**分工 + 交叉引用**（不搬家不重复）；执行模式 fast-track；立项后立即调度。

## Goals / Non-Goals

**Goals:**

- 新章 `07-safeguards.md` 让人类读者建立「框架靠什么保证不出事」的完整心智模型：每类机制的目的、原理、控制点三要素齐全，机制之间衔接为纵深防御叙事。
- 编号迁移零断链：4 个文件重命名 + 35 处交叉引用（含 `#锚点`）全部修订，README 目录表与导语同步。
- 内容以代码为准：章内出现的模块名、文件名、配置键、hook 名全部在仓库中可 grep 实证。

**Non-Goals:**

- 不重写 06 章、不迁移其参数口径（只在其头部加指向新章的交叉链接）。
- 不为每个机制写操作手册级细节（参数默认值/范围留 08 章配置参考与 06 章）。
- 不新增任何代码、hook、配置项；纯文档变更。

## Decisions

**D1 插入为 07 并整体顺延重编号**（用户已选）。备选是追加为 11 章避免 churn，但用户明确要主题顺序：保障机制紧随治理规则，二者是「机制的原理」与「机制的参数」的姊妹章。代价是 4 文件重命名 + 35 处引用修订，用 `git mv` 保留历史 + grep 清零验收兜底，成本可控。

**D2 与 06 章按「原理/参数」分层分工**。新章回答 why & how-guard（机制防御哪类事故、在哪拦截、违规后果），06 章保留数值口径（预算多少、退避几秒、告警几级流向谁）。两章互链。备选「新章为唯一权威、06 章瘦身」被否：一次性动两章、验证面翻倍，且 06 章的参数口径自成体系并无错误。

**D3 散文体为硬性文风约束**。用户明确要求「流畅供人类理解，避免只是罗列信息、避免一两句构成的短段落」：每个机制小节以连贯散文段落展开（段落须充分论证，非两三句即止），章节间有叙事衔接（从事故类型引出机制层次），表格/列表只作辅助汇总，不得以清单为主体。

**D4 盘点以代码为准、起点清单不设上限**。SPEC 给出五类机制的起点清单（见 spec 场景），实现者必须逐项对照代码核实并允许增删——发现 SPEC 未列的机制（如 fingerprint 缓存、frozen 场景门、bug-found 改道门）应纳入，发现已退役机制（如自引用符号链接）不得写入。

## Risks / Trade-offs

- [机制描述失真（凭记忆写错模块名/触发时机）] → 验收场景要求章内机制名/配置键/hook 名 grep 实证存在；写作时每节对照源文件核实。
- [重编号断链残留（锚点链接易漏）] → tasks 拆出独立步骤；验收场景要求全目录 grep 旧文件名零命中。
- [与 06 章口径漂移（两边都讲告警但数值不一致）] → 分工边界写入 spec 场景：新章不展开参数数值，只链接 06 章。
- [文风不达标（LLM 写作倾向罗列）] → 文风作为独立 Requirement + 可机械抽验的场景（段落充分展开、无清单主体），judge 按场景裁。
