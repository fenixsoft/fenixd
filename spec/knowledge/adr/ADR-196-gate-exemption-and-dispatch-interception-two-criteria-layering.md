# ADR-196：内容闸门豁免与派发拦截两判据分层——豁免只免冻结与告警，不放行派发

date: 2026-09-29
status: accepted

## Context

已交付 spec（实现已合并、验证通过）被外部 STATE 重置打回 ready 后，目录仅存 `verification-report.md`——内容完整性闸门按「空 spec」冻结并挂 major 告警，处置方向与事实相反；更早的实证（2026-09-12）中，被重置的已交付 spec 在 05:42Z 合并实现后被 06:33Z 盲目重实现。直觉修法是把 verification-report.md 加进认可内容名单让闸门放行——但这会让派发层把「已交付未归档」当成「可实现」，直接复刻盲目重实现事故。

## Decision

- 内容闸门与派发内容判据保持两套独立判据、分层管辖：
  - **闸门侧（冻结/告警处置）**：终态（done/pushed/archived）短路豁免——只免「冻结 + 告警」，不新增任何派发放行语义；非终态「已交付未落盘」（无认可内容但存在 verification-report.md）降级为独立信号 `spec_delivered_no_content`，不冻结、引导人工裁决（补 tasks.md 归档凭据或明确废弃）。
  - **派发侧（`spec_has_content` 四类认可名单）**：判据不动，verification-report.md 是验证产物而非起草内容，MUST NOT 进认可名单——已交付未落盘目录照样拦截派发、回滚派发槽。
- 终态 spec 出现在派发队列本身属异常，由派发层状态机语义管辖（非法 transition 被拒），不由本闸门越权代管。
- 该分层的代价被有意控制在「多一条待裁决告警」：最坏情形是已交付 spec 停在 ready 等人工裁决，无预算损失路径（派发始终被拦）。

## Consequences

- 已交付未落盘的 spec 不会静默自动放行，也不会被封进 blocked 丢失裁决上下文；其归宿由人工裁决（补归档凭据或明确废弃置终态）收口，告警以仅终态自动闭环的条件保持待处理可见。
- 后续 SPEC 扩展认可内容名单（如新增文件类型）时必须重新对照「盲目重实现已交付成果」这一失败模式论证，不得以「让闸门少告警」为由把验证产物混入认可名单。
- 「终态豁免」类处理成为闸门处置的先例范式：闸门后续新增处置分支时，豁免/降级只作用于冻结与告警面，派发面的放行必须显式另行论证。
