# UI 原型确认环（fenix-prototype）设计

日期：2026-10-29
状态：draft（brainstorm 定稿，待 builder check 后转 fenix-new 立项）

## 意图与动机

fenix 框架对无 UI 需求的边界定义（交流、头脑风暴、SPEC）已运转良好，但带界面的需求靠语言描述很难精确：用户说不清想要的布局，agent 猜出来的界面与用户脑中差异大，返工发生在实现之后，代价最高。

方案：在 fenix-new 起草 SPEC 的过程中，若检测到**大范围前端界面改动**，先走一轮原型确认——根据工程约束（DESIGN.md、主题 token、技术栈画像）生成「真组件、假数据」的高保真 HTML 原型，由独立简易 HTTP 服务器伺服，用户在浏览器中**点选 DOM 元素并提出意见**，agent 消化批注迭代原型，会话内循环直到用户认可。批准的原型随 SPEC 入库，成为 UI 真相源，对后续 AI 开发产生**约束力**。

核心价值排序：约束力 > 保真度 > 便利性。纯视觉参照的原型对后续开发没有约束力，等于白做——这是本设计的立身之本。

## 目标

1. **通用机制**：能力建立在「栈画像」（stack profile）上，不绑定 antd/React。fenixd 框架支持任意语言与技术栈的工程。
2. **高保真**：原型使用工程真实的组件库渲染（React+antd 就真用 antd），主题、间距、字号来自工程约束注入，数据全是假数据。
3. **会话内迭代闭环**：独立简易 HTTP 服务器伺服原型并接收批注，不依赖 dashboard 的 web 服务，不改动 fenixd daemon。
4. **批注结构化回流**：用户意见以结构化 JSON（元素锚点 + 意见文本）落盘，agent 可编程消费。
5. **绑定力**：批准的原型连同截图落 SPEC 目录，SPEC Scenario 标注其为 UI 真相源；实现与原型冲突时，要么照原型改，要么升级用户裁决。

## 非目标

- **文件级代码搬移**：原型的复用含义是组件选型、props、布局结构照搬进实现，不是把原型文件直接当实现代码。把原型建进工程本体以获得文件级搬移，v1 不做。
- **Freehand 画笔批注**：v1 只支持点选元素 + 文字意见，不做画圈涂鸦。
- **实现后自动视觉回归**：实现完成后自动截图与原型比对，留作未来扩展。
- **非浏览器栈的高保真**：无法从浏览器加载组件库的栈（服务端模板、桌面 GUI 等），降级为纯 HTML/CSS 仿样，并在 SPEC 中显式标注「视觉参照、无约束力」。
- **依赖 dashboard / 改动 daemon**：能力落在 skill 层 + 派发提示词契约段，不改 daemon 代码。

## 反目标（出现即失败）

- 原型生成要求工程本体可构建、可运行（把头脑风暴阶段绑死在构建链上）。
- 批注依赖特定 IDE、浏览器扩展或外部 SaaS。
- 原型重新生成后，已有批注丢失或错位到无关元素（锚点漂移）。
- HTTP 服务器需要人工记忆清理（僵尸进程、端口占用累积）。
- 原型批准后实现者可以无感绕过（绑定力失效）。

## 约束

- 本机出网走代理：组件库资源**本地 vendored 缓存优先、CDN 兜底**，不能依赖外网可达。
- 用户可能从外部网络（frp 隧道、局域网）打开原型 URL：服务器绑定地址显式可配，启动时打印完整访问 URL。
- 端口避让：不与 dashboard、frp 已用端口冲突（随机高端口 + 冲突重试）。
- 中文交互与文档。
- 主体落地于 agent-config 的 skill 体系（与 fenix-new 同层）；允许改动 fenixd 仓的派发提示词配置（`agents/*.md` 契约段），但**不改 fenixd daemon 代码**。

## 用户已拍板的决策

1. **迭代发生在会话内**：出原型 → 用户批注 → agent 修订 → 用户刷新再看，直到满意；不走异步 dashboard 审批流。
2. **独立简易 HTTP 服务器**：python 标准库实现，不依赖 dashboard web 服务。
3. **触发判定**：无界面、或界面小范围局部修改 → 不触发原型确认；大范围界面改动 → 触发。判定由 agent 在交流中做出（新页面/新大面板/布局重构/多区块联动视为大改），无硬性数值阈值；用户可随时主动要求出原型，也可对大改豁免——用户一票否。
4. **约束力硬要求**：纯视觉参照不可接受；v1 通过「真组件渲染 + 原型入库为 UI 真相源 + 冲突升级用户」达成。
5. **绑定力执行面**：v1 同时改 fenixd 仓 `agents/implementer.md` 与 `agents/code-review.md`，加**条件式**契约段——仅当 SPEC 声明原型为 UI 真相源时生效：实现前必读 `specs/<spec>/prototype/`、评审须对照原型检查、实现与原型冲突即升级用户；对无原型的 SPEC 零影响。绑定走双通道：SPEC Scenario 声明（与数值纪律同通道）+ 派发提示词契约段。

## agent 拍板的决策（builder 可复议，文档内视为已定）

- **形态**：独立 skill `fenix-prototype`。fenix-new 检测到大改时调用；也可被用户单独调用，迭代既有原型或对旧 SPEC 补原型。
- **栈画像机制**：生成前侦察工程（依赖清单识别组件库与版本、主题/设计 token 文件、DESIGN.md、现有页面样例），产出画像数据注入生成 prompt。v1 只实现 React+antd 画像（本工程吃狗粮实证），画像接口留扩展位。
- **真组件加载路线**：skill 自维护一份**与工程无关**的预打包 vendor 缓存（node 打包工具把 react+antd 按版本预打包；此缓存不要求工程本体可构建，不触碰反目标）。bootstrap 先做环境自检，按三级降级：预打包缓存 → CDN ESM 兜底 → 纯 HTML/CSS 仿样（显式标注「无约束力」）。node 是优先条件而非硬假设，降级路径逐级可见。
- **原型文件形态**：每个界面一张单文件 HTML，引用 vendored 组件库资源；关键区块打 `data-proto-id` 稳定锚（语义化命名，重新生成时优先保留既有锚），批注引用锚点而非裸 CSS selector，规避重生成后的选择器漂移。
- **批注器**：注入式 JS 脚本，与栈无关（纯 DOM 操作）：hover 高亮、点选元素、意见输入、意见列表面板、`POST /feedback` 提交；服务器不可达时降级为本地导出 JSON 文件。
- **服务器生命周期**：PID 文件管理；同一 SPEC 目录已有存活服务器则复用；原型批准或会话结束后回收；异常残留下次启动时探测并接管。
- **原型存放**：草稿迭代期放专用临时目录（建议 `.fenix/prototypes/<spec>/`，gitignore 口径与 `.history` 一致）；批准后落 SPEC 目录（如 `specs/<spec>/prototype/`），入库提交。整页截图为**尽力而为**：无头浏览器不可用或抓取失败时批准不阻塞，SPEC 显式记录「无渲染凭证」降级——HTML 是真相源主体，截图只是渲染凭证（批准门不因环境问题楔死）。
- **批准语义**：用户在会话中明示认可（如「原型定了」）才冻结；其后原型文件视为冻结，任何再修改 = 新一轮确认。SPEC 正文与 Scenario 显式引用原型路径并声明 UI 真相源地位。

## 留给 builder 的

- 栈画像 JSON 的具体字段与侦察脚本实现。
- vendored 组件库缓存的 bootstrap：首次在代理环境下抓取哪些版本、落盘位置、缓存失效策略。
- 批注 JSON 的 schema 细节（锚点、意见文本、时间戳、轮次号）。
- `data-proto-id` 的生成规则与重生成时的锚保持策略。
- 与 fenix-new skill 的衔接点：检测时机、调用方式、原型批准后回填 SPEC 的具体动作（需读 fenix-new 现有 prompt 结构后定）。
- 派发提示词契约段的落点：遵循 `agents/*.md` 现有契约段惯例，条件开关 = SPEC 内的 UI 真相源声明，措辞需保证对无原型 SPEC 的零影响。
- 批注器 UI 的具体交互细节（意见面板位置、快捷键、移动端可用性不做硬要求）。

## 验收场景（建议）

以本工程在途的界面需求（如 agent-card-redesign）做首次端到端实证：fenix-new 交流中触发原型 → 浏览器批注 ≥2 轮迭代 → 批准入库 → 实现阶段能从原型直接读出组件选型与布局结构，实现与原型冲突时按约束力条款升级，且派发提示词契约段在带原型的 SPEC 上真实生效（评审侧能对照原型提出冲突）。
