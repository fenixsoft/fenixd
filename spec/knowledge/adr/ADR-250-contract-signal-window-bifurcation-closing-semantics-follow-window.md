# ADR-250：契约信号按触发窗口二分，处置收尾语义随窗口而非随信号类型

date: 2026-10-07
status: accepted

## Context

验证契约（verify.yaml）缺陷的检测原有唯一触发点：spec 推进到验证消费时的轻量自证 fail-fast。而 fenix-init 无条件向每个新项目写入全注释模板（解析为 None），首个 spec 首次推进到验证段必然卡 blocked 等待自主起草——契约起草本可与规划/实现并行，却被串行压在验证消费点（实测单次卡 26 分钟、连发 2 个 admin run，其中先派 run 整轮空转）。把同一信号（`verify_contract_missing`）的触发时刻前移到实现期巡检后，一个信号类型开始服务两个触发窗口，而两个窗口里 spec 的处境不同：消费期触发时 spec 已被验证失败打断，「spec 复位 ready 触发重验证」是合法收尾；前置窗口触发时 spec 可能有活跃实现 run，且 IMPLEMENTING→READY 属合法状态转换，机械复位会把进行中的实现打回重做、与活跃 run 收尾竞态。

## Decision

契约信号按触发窗口二分、互斥不双发：ready/implementing 窗口由 admin_monitor 周期巡检前置检测（文件存在但解析不出顶层映射才触发，文件缺失维持「无契约回退」既定语义不触发），testing 及之后由验证消费期轻量自证 fail-fast 权威检测，同一形态同一时刻只归一个窗口。处置收尾语义随触发窗口而非随信号类型：消费期窗口保留「spec 复位 ready 触发重验证」收尾；前置窗口的收尾是「起草落位即可、勿复位 spec 状态」，由信号 description 显式注明，Administrator 不得沿用消费期收尾。起草质量门与窗口无关——三段自证全通才落位生效。

## Consequences

- 新项目首个 spec 不再在验证消费点串行阻塞，契约起草与实现并行，重复 admin run 成本消除。
- 后续给 `verify_contract_missing` 增加任何新触发点必须归入两个窗口之一并携带匹配的收尾指引；只加触发不标窗口语义，会把复位类收尾漏进实现期场景。
- 前置起草的契约可能早于实现定形而失准——由既有权限边界（明显失效可修且留痕、有效契约不碰）与消费期 mtime 门（契约变化时重证）兜住，不另设失效检测机制。
- 两窗口互斥是硬约束：触发面一旦重叠即双发信号、重复唤起 Administrator。
