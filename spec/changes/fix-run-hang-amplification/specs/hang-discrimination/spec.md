# Spec Delta: hang-discrimination

## ADDED Requirements

### Requirement: 活性判定输入包含「无实质进展」信号
活性判定（`_liveness_snapshot` / `_judge_liveness`）的证据输入 MUST 在既有维度（窗口内事件数、工具调用计数与类型分布、最后事件间隔、最后输出片段）之外，纳入「无实质进展」信号：
- **重复相似操作占比**：窗口内工具调用按「工具名 + 规范化入参指纹」聚类，取最大同指纹簇的调用数占窗口内总工具调用数的比例；
- **后台子进程零产出指示**：该 run 在窗口内等待的后台任务（背景 Bash / 子进程）若有「进程存活但输出文件大小在窗口内零增长」的情形，记为一条停滞指示。

新增信号 MUST NOT 改变既有字段语义，仅为判定提供增量输入。

#### Scenario: 重复相同工具调用占比超阈
- **WHEN** 某 run 的判定窗口内工具调用共 100 次，其中同一「工具名 + 同参数指纹」的调用占 60 次，重复占比 0.60
- **THEN** 快照中 `repeat_ratio`（或等价字段）MUST 反映该占比，且该值 MUST 参与后续停滞判定

#### Scenario: 后台子进程存活但零产出
- **WHEN** 某 run 在窗口内持续等待一个后台子进程，该进程存活但其输出文件大小在窗口内无增长
- **THEN** 快照 MUST 记录该停滞指示，且该指示 MUST 参与后续停滞判定

### Requirement: 重复占比超阈时确定性判停滞，不再调用判定 LLM
当窗口内重复相似操作占比达到或超过固化阈值时，系统 MUST 直接判定该 run 为 `stagnant`（确定性短路），MUST NOT 再发起判定 LLM 调用。判定口径 MUST 显式排除「持续产出事件或 I/O 增长」作为 `advancing` 的充分依据——事件与 I/O 的持续增长不再能单独支撑「真实推进」结论。

阈值 MUST 为固化常量（依据本案样本：单窗口内数百次调用中，死循环表现为极高比例的同指纹重复），经 design 固化并在代码注释中标注样本依据。

#### Scenario: 短路不产生 LLM 调用
- **WHEN** 窗口内重复相似操作占比达到阈值，到达墙钟时限触发活性评估
- **THEN** 系统 MUST 直接给出 `stagnant` 判定并进入终止路径，MUST NOT 发起任何判定 LLM 子进程调用

#### Scenario: 事件与 I/O 持续增长但操作重复
- **WHEN** run 流在窗口内有大量新增事件（如心跳与工具进展事件）、CPU 与磁盘 I/O 持续增长，但其中绝大多数为同指纹重复操作
- **THEN** 判定结论 MUST 为 `stagnant`，MUST NOT 因「事件在增长」判为 `advancing`

#### Scenario: 真实推进不被误判
- **WHEN** 窗口内工具调用为多样化的不同操作（不同文件读写、不同命令、含产出型工具调用），重复占比低于阈值
- **THEN** 判定 MUST 允许结论为 `advancing`，且续期行为与既有语义一致

### Requirement: 挂起判别全程留痕
每次因重复占比短路或纳入停滞指示而做出的判定 MUST 写入被监督 run 的 jsonl 与 daemon 日志，证据摘要 MUST 包含重复指纹的构成（如「top fingerprint: `<tool>(<args-hash>)` ×N，占比 0.xx」），使事后复盘可区分「确定性短路的挂起」与「LLM 判定为停滞」。

#### Scenario: 短路判定可审计
- **WHEN** 一次判定由重复占比短路产出
- **THEN** run jsonl 与 daemon 日志 MUST 各留下一条该判定记录，且证据摘要 MUST 指明短路原因与重复指纹构成
