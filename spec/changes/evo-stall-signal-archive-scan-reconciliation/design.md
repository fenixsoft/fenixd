# 设计：停滞信号扫描面归档盲区对账

## 根因证据链

- 扫描面：两个停滞信号面共用 runs 目录顶层 glob（core/admin_monitor.py:4459-4461），不含 archive/；重启重建（既有 design 3.2）同样只重建顶层在盘文件。
- 归档节奏：runs 保留清理约 5 分钟一拍（daemon 日志序列 19:23:23→19:28:24→…），终态到归档延迟 0-5 分钟均匀分布；巡检节拍同 5 分钟（.fenix/config.yaml:120）。
- 实证：历史 4 组落账擦边（窗口 150s/124s/80s，落账仅比归档早 148s/27s/4s）；2026-11-25 窗两例（136s/28s 窗口）窗口内无巡检轮即漏——竞态结构性存在，夜审每日产生大停滞 run，漏报迟早复发。
- 与 7a6362592 的边界：该修复堵「stat 瞬时失败永久零入账」窄缺陷，不改扫描面；本设计的扫描面扩展与其正交。

## 方案选型

- 扫描面扩展（治本）：信号扫描循环从 glob("*.jsonl") 扩为顶层+archive/ 双源。备选「归档事件时点触发补充入账」依赖保留清理侧回调，跨模块耦合更大，不采用。
- 对账自证（兜底）：以终态 run_metrics 行合计为基准对账内存累计器，差额超 60 秒补发信号并注明对账来源。备选「累计器落盘」只解决重启续算，治不了归档盲区（重启重建也只扫顶层），不作为主方案；对账自证不依赖根因裁定，两假说（stat 瞬时失败/扫描面竞态）任一成立时都能兜住。
- 去重：沿用既有 run 级去重集合，三来源（顶层/归档/对账）共用同一键空间；对账补发信号带来源注记避免与常规信号混淆。

## 实现插入点

- core/admin_monitor.py：扫描循环处（约 4459-4461）扩展档案源列表；对账自证逻辑挂在 _evaluate_lane_stall_daily_signals 同一巡检轮内（约 4339 起）；内存态累计器字段（:2226-2238）不变。
- 去重集合与信号落账复用既有通道，不新增信号 kind。

## 风险

- archive/ 随保留清理增长，扫描量增大：只扫当日 UTC 日桶相关档案（按 mtime/文件名时间过滤）可控；归档件总量有限（runs 保留策略约束）。
- 对账补发与常规信号重复：R3 去重键约束 + 补发信号 evidence 注明对账来源，可审计可区分。
