# 设计：陈旧自愈跨批次合流窗

## 落点与状态

- 判定入口：fenixd.py `_maybe_stale_selfheal_tick`（:2411，主循环 1s 粒度）。检测本身沿用 `_update_stale_code_state`（30s 重算）不动。
- 合流状态：复用 `_stale_idle_since`（空闲计时）隔壁新增「合流期边沿计数」与合流态维持所需的最近陈旧边沿/最近按闸自愈重启时刻，从内存状态维护。复位条件是「悬置消化（磁盘 mtime 不再超 baseline）**且**合流静止期届满（距最近一次陈旧边沿或最近一次按闸自愈重启——取较晚者——达 coalesce_idle_seconds 无新边沿）」；按闸重启导致的消化不复位合流态——否则重启后新进程 baseline 即刷新、悬置立即消化（`_update_stale_code_state` 真→假边沿），下一批（10-18 窗实测距上批重启仅 9-17 分钟）将重回基础闸，五连重启形态原样复现。重启事实以 restart_history.jsonl 既有记录（仅自愈路径写入，ts 即重启时刻）做幂等推导、双向防错：最近记录在合流静止期内 → 新进程延续合流态（防状态丢失后误回退基础闸）；记录超窗/无记录 → 按新周期基础闸（防把陈旧重启史误算进当前合流期）。

## 参数

- coalesce_idle_seconds 缺省 1800s：10-18 窗批间隔 20-28 分钟，1800s 恰覆盖单批间隔上限；同时远小于 4h 强转与既有 1800s 冷却滑窗，不产生新的循环风险。
- 基础闸 idle_confirm_seconds（600s）与其项目级覆盖（config.py:2239 模式）不动；coalesce_idle_seconds 同样支持项目级覆盖。
- 影响权衡：首批仍 600s 生效；合流期内第二批起的生效延迟最坏为末批边沿 + coalesce_idle_seconds（缺省 30 分钟）。持续连发（批间隔恒 < 合流闸）下合流闸持续不满足，由 4h 悬空强转兜底收尾——修复生效延迟的绝对上界是 max_dangling_seconds 而非 30 分钟。另：连发期间关键路径 preflight 命中陈旧预检即旁路请求重启（本方案保留其即时语义），合流窗可能被关键路径操作提前截断，属接受的影响面。

## 与既有机制交互

- 4h 悬空强转：优先级最高，合流闸不得拦截（强转是防陈旧永不生效的兜底）。
- 防循环冷却（config.py:2211-2215，fenixd.py:2600-2608）：语义不变，合流等待期间不发生重启故不计次；一旦执行重启照常计次，合流不是冷却豁免。
- preflight 请求通道（core/code_stale_flag.py request_restart）：旁路合流闸——该通道语义是关键路径（收尾提交/蒸馏派发/admin choice）即时生效，被合流闸延迟会破坏 evo-add-key-path-stale-code-preflight 的目标（小时级→分钟级）。
- drain 在飞保护：不动（fenixd.py:5217-5247 排水窗口/排水集合 + supervisor 优雅重启链路）。

## 观测

- 合流等待日志行：每次合流期内检出的边沿记「stale coalesce: 第 N 次边沿等待，闸值 Xs」（info 级）；执行重启时记合流收敛结果（本周期共 N 次边沿、合并为 1 次重启）。
- 不新增终态 run_metrics 字段（重启属 daemon 面，与 run 记账解耦）。

## 风险

- 框架自研单批场景（批间隔 >1800s：静止期届满、合流态复位）不受影响；批间隔 <600s 的密集场景仍由既有 600s 收编窗处理；600s–1800s 的批间隔正是收敛目标带（10-18 窗 20-28 分钟批间隔落于此）。
- 状态在 daemon 意外退出时丢失：以 restart_history 最近自愈重启时刻做幂等推导，避免重启后合流状态错乱。
