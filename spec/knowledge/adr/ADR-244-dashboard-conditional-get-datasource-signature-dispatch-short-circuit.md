# ADR-244：dashboard GET 读端点条件请求通道——ETag 取数据源签名、分派层短路、宁缺 304 不假 304

date: 2026-10-07
status: accepted

## Context

dashboard 读路径的传输浪费是「无差别 2s refresh 心跳 × 无上限全量载荷 × 无协商缓存」三者的乘积（实测运维页挂 1 小时 ≈ 190MB）。补协商缓存时面临选型：对响应体做哈希则每次 304 判定都要先序列化，省传输不省计算；而单进程 `ThreadingHTTPServer` + keep-alive 响应纪律、部分 route 为自写响应的自含 handler（如 `_api_config_get`，不返回 payload），都对 304 的实现位置与写出路径提出了约束。

## Decision

全部 GET 读端点默认挂 ETag，取值为响应实际依赖数据源全集的 `(mtime_ns, size)` 签名组合哈希——只 stat 不读内容，签名源宁多勿漏、禁止不完整签名；协商短路实现于表驱动路由分派层，发生在 route handler 调用之前（兼容自含响应 handler），304 与 `_json` 同一写出纪律（不发体、不写 Content-Length），keep-alive 不被污染；签名函数缺失/抛错/返回空一律降级无条件 200 路径——宁缺 304 不假 304；`_json` 发头前按签名上下文复核一次，防签名计算与取数两趟读取间隙内数据变化导致旧签名错标新体。后续新增 GET 读端点必须注册签名函数并遵守同一纪律；文件签名禁以 path 为键跨请求 memo 化 stat（「写后立刻读」窗口吐陈旧签名即假 304），安全 memo 只允许单轮内去重与以完整签名集为键的树哈希复用。

## Consequences

- 数据未变时传输归零（350KB 级全量体 → 约 200B 响应头），304 路径零序列化；计算侧增量缓存（SummaryIndex、overview 结果缓存）与本通道正交叠加，各自只治一端。
- 付出每请求对签名源的 stat 成本（防假 304 禁止跨请求缓存 stat），以安全 memo 把同一窗口内的重复哈希与重复 stat 压到常数。
- mtime/size 签名存在同字节同 mtime_ns 窗口的漏检窗口（≤1 心跳周期，2s），依赖下一心跳自愈——与心跳本身最终一致的现状同级，可接受。
- 前端请求层以模块级 Map 缓存承接（304 判定先于 `!res.ok`、304 命中交付结构化拷贝防共享条目污染），对调用方透明、接口不变形。
