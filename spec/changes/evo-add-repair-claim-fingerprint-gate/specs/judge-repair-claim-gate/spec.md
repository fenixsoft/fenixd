# judge-repair-claim-gate 能力规范

## ADDED Requirements

### Requirement: bug-found 派修复随单附失败指纹
框架经 bug-found 路由派发实现者修复时，MUST 在修复任务上下文中附被修场景的失败指纹（场景 id 与失败断言签名摘要，读裁决面既有指纹数据，不新造指纹体系），使实现者申报自检与受理门比对使用同一口径。无可附指纹（如无基线的首轮修复）时 MUST 照常派发，不因指纹缺失阻断。

#### Scenario: 派单上下文携带指纹
- **WHEN** judge 裁决产生 bug-found 且路由派发实现者修复
- **THEN** 修复任务上下文包含被修场景 id 与失败签名摘要，与裁决面指纹数据（verdict_cache 场景指纹 / verdict_stability 轮级 stamp）同源

#### Scenario: 无基线不阻断
- **WHEN** 被修场景无可用的既有失败指纹（首轮修复）
- **THEN** 照常派发，受理门对该轮申报不做指纹比对（放行）

### Requirement: 修复申报受理指纹门
框架受理 product 类修复申报（repair claim）时（fix SPEC 完成消费点与 fastlane 子集重验消费点），MUST 对被修场景的新鲜侧指纹与派单指纹比对。新鲜侧指纹源优先级：实现者申报内探针标注（主）→ 盘面 post-fix 新鲜轮指纹（有新鲜轮时）；两者皆缺按「缺探针标注」拒收；MUST NOT 以受理时点的 verdict_cache 缓存条目直接作新鲜侧（该缓存仍为派单同轮数据，比对恒等）。指纹未变化（同一失败签名原样复现）时本轮修复 MUST 被拒收——不重入执行、按既有拒收语义记账（rejected）并留痕，拒收信息含「失败指纹未变化」与双方指纹值，经既有重派上下文回传下轮；指纹已变化、场景已转 pass 或无基线时照常受理。本门 MUST NOT 改变修复预算上限、预算记账口径与耗尽持久态语义，MUST NOT 改变既有 test-defect 场景修复通道（pipeline.py:1970/2007/2029 三处调用点）的行为。

#### Scenario: 指纹未变化拒收
- **WHEN** 实现者申报修复完成且被修场景新鲜侧指纹（探针标注或新鲜轮指纹）与派单指纹一致
- **THEN** 本轮修复被拒收：记账 rejected、spec 保持当前验证态、不重入执行场景集、拒收信息含「失败指纹未变化」与双方指纹值

#### Scenario: 指纹变化照常受理
- **WHEN** 被修场景失败指纹已变化（失败集收缩或签名改变）或场景已转 pass
- **THEN** 照常受理并进入既有后续流程，行为与本门引入前一致

#### Scenario: 预算口径不变
- **WHEN** 本门拒收发生
- **THEN** 修复预算按既有口径记账（rejected 计数），预算上限与耗尽持久态语义不变

### Requirement: 实现者修复申报真机探针义务
实现者完成 product 类缺陷修复申报收尾时，MUST 附被修场景的最小真机探针结果（针对修复后产物——重建/重载后实例或构建——的单场景执行或 API 级探针复跑）并标注探针失败签名与派单指纹是否一致；探针复现派单指纹时 MUST NOT 申报修复成功。探针 MUST NOT 对未加载修复的旧运行实例取证。申报缺探针标注时受理门 MUST 按指纹门同语义拒收。本义务 MUST NOT 扩大为全量回归义务（全量重验仍由验证链承担）。

#### Scenario: 探针复现派单指纹不得申报成功
- **WHEN** 实现者真机探针复现派单失败签名仍申报修复成功
- **THEN** 该申报被拒收（受理门按指纹未变化语义），实现者按探针结果继续修复或如实申报失败

#### Scenario: 探针签名变化正常申报
- **WHEN** 实现者探针失败签名与派单指纹不同或场景转 pass
- **THEN** 申报照常进入受理流程，由受理指纹门做最终比对

#### Scenario: 不扩大实现者回归义务
- **WHEN** 实现者完成修复申报
- **THEN** 义务范围限于被修场景最小探针，MUST NOT 引入全量回归义务
